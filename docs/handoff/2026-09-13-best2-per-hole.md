# 設計：ベスト2ボールを「ホール別に上位2名」方式へ作り替える — 2026-09-13

**種別**: M/L（★**§3.4 の計算仕様そのものを差し替える load-bearing 変更**・要前後比較）
**発端**: ユーザー確定（2026-09-12）
> 一般に「ベスト2ボール」と呼ばれるのは「各ホールごとに上位2名を採用して18ホール分足す」方式：**こちらを意図しています**

**本設計**は **ホール別に上位2名を採用して18ホール分を合計**する方式へ一律に差し替える。

## 2. 現状（コード実測・2026-09-13 HEAD = `3ef2051`）

### 2.1 式

```js
/* js/calc.js（#186 修正後の現行） */
function best2(g,t){ const m=teamScoreMembers(g,t); if(!m.length)return null;
  const ns=m.map(pid=>netScore(g,pid)).sort((a,b)=>a-b); return Math.round((ns[0]+(ns[1]||ns[0]))*10)/10; }
```

- **ラウンド単位**：18ホール終わったあとのネットで2名を選び、その2名のネットを足す。採用者はラウンド中ずっと固定。
- 母数は `teamScoreMembers`（`teamMembers` ∩ 1H以上入力済み）＝**Issue #186 は 2026-09-13 の `3ef2051` で既に修正済み**（ただしラウンド単位のまま。§5.3 で構造的解消を確認する）。
- **1名のときは同じ人を2回足す**（`ns[1]||ns[0]`）＝「2ボール分の合計」という形は現行から一貫している。**本設計はこの思想をホール単位に移すだけ**。

**読み取れること（すべて実測）**

1. **A と C は別競技**。勝者が入れ替わるのは 10件中 **5件**（`best2Hole`／`blowup`／`solo`／p2／p6）。

   → PM 仮説「C の選択結果は A と同じでは？」は**否定**された。各人の HDCP が違うので順位が入れ替わる。
2. **2名チームでは C＝B＝現行の値**（数学的必然。2名チームは常に両名が採用されるので `Σ(adjHole − h/18) = effGross − periaHdcp = netScore`）。
   → C を選ぶと **2名チームでは「ホール別に作り替えた」ことが数値に1ミリも現れない**。
3. **D は A とほぼ同一**。10件中 p5 だけが動き（`211→209`／`168→166`）、**勝者は全件不変**。
   大叩きフィクスチャ（`blowup`＝par+7 が3ホール）ですら **A と D が完全一致 `[124,110]`**。
   → 「上位2つだけ採る」時点で大叩きは既に捨てられており、**ダブルパー上限は仕事をしない**。
4. **B は引き算の対象が恣意的**なぶん、A とも C とも違う勝者を出す（`blowup`＝レッド／`best2Hole`＝ブルー／`solo`＝グリーン）。「誰の HDCP を引くか」に正解が無いまま勝敗が動く。

### 3.3 決定：**案 A** を採る

> **ベスト2ボール = Σ_{i=0..17}（そのホールで入力済みメンバーの `adjHole` のうち小さい方から2つの和）。小さいほど良い。**

**根拠**

| # | 理由 | 裏づけ |
|---|---|---|
| 1 | **投影して検算できる**（CLAUDE.md 投影前提 §11.14） | A なら「スコア表に**印字されている数字**の小さい方2つ」。C は各人ごとに `HDCP/18`（例 32.4→1.8）を引いた**画面に出ない実数**で採用者が決まる。後方席の参加者に「なぜこの2人？」を説明できない |
| 2 | **アプリ内の全ホール別計算と同じ土俵** | `holesWon`（HBH）／`m1HoleWin`（1on1）／`vAdj`（ベガス）／スコア表の `.winc` は**すべて `adjHole` 基準**。best2 だけ4つ目の基準を作らない |
| 3 | **ゴルフの慣例に反しない** | 正式な per-hole ネット（WHS 4BBB）は**ホールハンデ指数に沿って1打ずつ配分**する。アプリに指数が無い以上 A（グロス）か「非対応」の二択で、**等分配分（C）は現実のどの競技規則にも存在しない**。日本のコンペ解説も「各ホールで最も少ない打数のスコアを採用」＝グロス記述が主流 |
| 4 | **HDCP が消えても大会は壊れない** | チーム戦の勝ち点は種目別の合計（§11.15）。**ネット対抗**がハンデ系の柱として並存し、個人戦のネットも別にある。加えて **A でもエブリ（女性 −1/−2）は各ホールで効く** |
| 5 | **実装と説明が1行で済む** | ルール説明が「各ホール上位2名の打数を足す」で終わる。C は「隠しハンデを18で割って各ホールから引く」という、幹事が口頭で説明できない仕様になる |

**A で失うもの（明記して受け入れる）**: ダブルペリアの HDCP がベスト2ボールに効かない＝**上手い人が2人いるチームが有利**。
これは「ベスト2ボールはグロスの競技」という定義変更であり、i18n のルール説明（§8）に**明示する**。

### 3.4 決定：ダブルパー上限（D）は**付けない**

実測（§3.2-3）のとおり効果が無いのに、`g.vegas.cap` のようなオプションを増やすと設定・保存・i18n・回帰が増える。
**将来必要になったら `vAdj` と同じ1行（`Math.min(v, 2*g.par[i])`）で足せる**ことだけ §11 に記録する。

### 3.5 将来の seam（今回はやらない）

コースマスタに**ホールハンデ指数**（`courses[].nines[].si`・9要素）を持たせた日に、
`best2HoleVal(g,pid,i)` を `adjHole` から「`adjHole − (指数配分ストローク)`」へ差し替えれば**正式な per-hole ネット**になる。
**そのために、ホールごとの1名分の値を返す関数を1本に切り出しておく**（§4.2 の `best2HoleVal`）。C を今やらない代わりの保険。

## 4. 決定：計算仕様（★§3.4 を差し替え・load-bearing）

### 4.1 式（前 → 後）

```
# 前（現行・ラウンド単位ネット）
M(T)      = teamScoreMembers(g,T)                         # teamMembers ∩ 1H以上入力済み
ns        = sort_asc({ netScore(pid) | pid ∈ M(T) })
best2(T)  = M(T)=∅ ? null : round1( ns[0] + (ns[1] ?? ns[0]) )

# 後（ホール別グロス・本設計）
M(T)      = teamScoreMembers(g,T)                         # ★母数は変えない
v(T,i)    = sort_asc({ adjHole(g,pid,i) | pid ∈ M(T), adjHole ≠ null } )   # そのホールの入力済み打数（エブリ適用後）
hole(T,i) = |v| = 0 → null                                # 誰も入力なし（未入力／未開封）＝そのホールは数えない
          = |v| = 1 → v[0] × 2                            # ★1名しかいない＝その1名を2回採用（§5.1）
          = |v| ≥ 2 → v[0] + v[1]                         # 上位2名
used(T)   = #{ i | hole(T,i) ≠ null }
best2(T)  = used(T) = 0 ? null : Σ_{i: hole≠null} hole(T,i)
```

- **方向は `'asc'`（小さいほど上位）＝不変**。`add()` のシグネチャ・同点山分け・`live<2` ガードは**1文字も変えない**。
- **丸め（`Math.round(v*10)/10`）は不要になる**。`adjHole` は整数（生スコア − エブリ 0/1/2）なので合計は必ず整数。
  丸め呼び出しを**消す**（残しても値は同じだが、「小数が出る計算だ」という誤解を残さない）。表示側 `renderTeams` の `Math.round(r.v*10)/10` は触らない（整数に対して恒等）。
- **値のスケールが変わる**: 現行は「ネット2人分」≒120〜150、新方式は「**グロス2人分**」≒140〜180（パー72のコースなら 144 が基準）。カードの数字が大きくなるのは正常。

### 4.2 実装案（`js/calc.js`・この形で書くこと）

```js
/* ---- ベスト2ボール（§3.4・docs/handoff/2026-09-13-best2-per-hole.md が正）----
   ★2026-09-13 方式変更（load-bearing）: ラウンド単位のネット上位2名 → 「各ホールごとの上位2名を18ホール合計」。
   判定値は adjHole（エブリ適用後の打数）＝ホールバイホール/1on1/ベガス/スコア表と同一基準。
   ダブルペリアHDCP は効かない（アプリにホールハンデ指数が無く、等分配分は競技規則に存在しないため。設計 §3.3）。
   ・入力が1名しかいないホールは、その1名を2回採用（ラウンド単位時代の ns[1]||ns[0] と同じ思想・設計 §5.1）。
   ・誰も入力していないホール（未入力／未開封）はそのホールを飛ばす＝開封に応じた暫定集計になる（設計 §5.4）。
   ・母数は teamScoreMembers（#186 で新設）。ホール別では adjHole が null を返すので未入力者は構造的に入らないが、
     意図の明示と b2ScSel との共有のため据え置く（値は teamMembers 全員でも同一＝実測 145=145・設計 §5.3）。
   ・値は整数（adjHole が整数）＝0.1 丸めは不要。 */
function best2HoleVal(g,pid,i){ return adjHole(g,pid,i); }   // ★将来ホールハンデ指数を導入する差し替え点（設計 §3.5）
/* そのホールで採用される2ボール。pids は強調表示用（同値は teamScoreMembers の順＝memberIds 登録順・安定ソート）。
   dbl=true は「1名しかいないので同じ人を2回採用した」印（表示で ×2 を併記する・§7.2） */
function best2HolePick(g,T,i){
  const rows=teamScoreMembers(g,T).map(pid=>({pid,v:best2HoleVal(g,pid,i)}))
    .filter(r=>r.v!=null).sort((a,b)=>a.v-b.v);
  if(!rows.length) return null;
  const two = rows.length>=2 ? [rows[0],rows[1]] : [rows[0],rows[0]];
  return { pids:[...new Set(two.map(r=>r.pid))], sum:two[0].v+two[1].v, dbl:rows.length<2 };
}
function best2(g,T){ let s=0,used=0;
  for(let i=0;i<18;i++){ const p=best2HolePick(g,T,i); if(p){ s+=p.sum; used++; } }
  return used? s : null;
}
```

- `teamWinPoints` の `add('best2ball', teams.map(t=>best2(g,t)),'asc')` は**そのまま**（差し替え不要）。
- **`Array.prototype.sort` は安定**なので、同打数のときに採用される「顔」は `teamScoreMembers` の順（＝`memberIds` 登録順）。
  合計値は同値なのでどちらを採っても同じだが、**強調表示の再現性のためにこの規則を正とする**（現行 `b2ScSel` の規律を踏襲）。

## 5. 決定：境界ケース

### 5.1 ★1ホールに2名そろわないとき ＝「1名を2回採用」

**実データで起きる**：アプリ内テストデータ **p6 チームブルー**（`cut:12` ＝ 13番以降が未入力）が該当。

| 方針 | p6 レッド | p6 ブルー | 結果 | 判定 |
|---|---|---|---|---|
| **①そのホールを飛ばす** | 180 | **118** | ブルー圧勝 | ✗ **12ホールしか数えないぶん丸ごと得をする**（6ホール×2ボール＝62打が消える） |
| **②1名分だけ足す** | 180 | **149** | ブルー勝ち | ✗ 「半ホール分」しか数えない＝やはり得をする |
| **③1名を2回採用（採用）** | 180 | **180** | **同点（山分け）** | ✓ 実態と一致 |

p6 の実態: レッド＝2名とも全18H・各90打。ブルー＝村田が全18H・90打／上原が12Hまで・同ペース。
**「同じ90打ペースの2名」対「90打ペースの1名＋12Hで止まった1名」は、2ボール換算で見れば互角**＝③の同点が正しい。

補強理由:
- 現行仕様の **`ns[1]||ns[0]`（1名チームは同じ人を2回）と同じ思想**。仕様の連続性がある。
- **18ホール×2ボール＝36ボール**という分母が常に揃う（①②は分母が縮む＝他チームと比べられない）。
- 「メンバーが1名のチーム」と「そのホールに1名しかいないチーム」が**同じ規則で処理される**（分岐が1つで済む）。

**チームを対象外にする案**は採らない（1ホール未入力があるだけで種目から消えるのは経過表示として使えない）。

### 5.2 メンバーが1名だけのチーム

18ホールすべてが §5.1 の「1名を2回」に落ちる＝**その人のグロス×2**。
実測 `solo` フィクスチャ: レッド（1名・`adjHole` 合計61）→ **122**。現行も 122（HDCP 0 のため偶然一致）。方式としては連続。

### 5.3 ★母数と Issue #186（実測で解消を確認）

| 確認 | 実測 |
|---|---|
| 未入力メンバー1名を含む4名チーム（p2 レッドの1名を全ホール null に） | 現行 `best2` = 133.6 ／ **新方式（母数 `teamScoreMembers`）= 145** ／ **新方式（母数 `teamMembers` 全員）= 145** |
| その未入力メンバーの `netScore` | **0**（#186 の原因） |
| 全員未入力のチーム | 現行 `null` ／ 新方式 `null`（`used=0`） |

> **#186 はホール別方式で構造的に解消する**：`adjHole` が `null` を返すので、未入力メンバーはどのホールでも候補に入らない。
> **母数を `teamScoreMembers` にしてもしなくても値が同一**（145＝145）であることを実測で確認した。
> ただし **母数は `teamScoreMembers` のまま据え置く**（①`3ef2051` の意図を消さない ②`b2ScSel` と同じ集合を使う ③「全員未入力＝`null`」の意味が読める）。

### 5.4 開封連動（`viewGame`）

`renderTeamGame` は `viewGame(g)`（開封済みホールだけ残したコピー）を渡す。未開封ホールは全員 `null` → `best2HolePick` が `null` → そのホールを飛ばす。

**実測（p2・開封ホール数ごとの値）**

| 開封 | レッド | ブルー | グリーン |
|---|---|---|---|
| 0H | `null` | `null` | `null` |
| 1H | 8 | 8 | 10 |
| 5H | 41 | 32 | 47 |
| 9H | 73 | 67 | 78 |
| 18H | **144** | **136** | **150** |

- 0H では全チーム `null` → `add()` の `live<2` ガードで**種目不成立**（勝ち点なし）＝現行と同じ挙動。
- 1ホール開けるごとに2ボール分ずつ増える＝**段階開封の演出に自然に乗る**（`renderTeams` の目隠し・発表ボタンは不変）。

### 5.5 `null` の扱い（呼び出し元）

| 呼び出し元 | `null` は起きるか | 対応 |
|---|---|---|
| `teamWinPoints` | 起きる（全員未入力チーム） | **対応不要**。`add()` の `live` 判定が従来どおり除外する |

> **先に main に入った方の実装をそのまま再利用し、二重に書かない**（実装者はリベース後に既存を確認すること）。

## 6. 決定：互換の扱い ＝ **モード分岐なしの一律切替**

| 選択肢 | 判断 |
|---|---|
| `g.best2Mode:'round'|'hole'` のような**コンペ別オプション** | **採らない** |
| **一律切替**（過去コンペの `best2` 値も新方式で再計算される） | **採用** |

**根拠**

1. **α運用のコンペは1ptも動かない**。`BETA_FMT` に `best2ball` が入っており、`chFormats(g)` は **α チャネルで `best2ball` を一律 `false`** にする（§11.12 C）。
   ＝α で運用した過去コンペは、**そもそも best2 を評価していない**（勝ち点・配分・表示のどこにも出ない）。
2. **β での実戦投入がない**（本種目は検証中のまま）。`2026-09-12-team-score-average.md` §0 が守ろうとした「あのとき優勝したのは誰か」という**記録は存在しない**。
3. **競技の定義そのものの変更**であって、幹事が選べる「集計オプション」ではない。2方式を残すと `best2` が2実装・`b2ScSel` が2実装・ルール説明が2種類・回帰が2倍になり、**β種目1つに対して不相応**。
4. 将来どうしても必要になったら、`best2HoleVal`（§4.2）と `best2` の2関数を分岐させれば足りる seam はある。

**実務上の影響**: β チャネルで過去のコンペを開くと best2 の数字が変わる（例 p2 レッド 133.6 → 144、順位も入れ替わる）。
**Issue 本文に「β種目の定義変更・過去コンペの best2 表示値は変わる（α運用のコンペは非影響）」と明記する。**
