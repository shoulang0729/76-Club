## 0. 結論（先に3行）

1. **#171 の「参照が残る」半分は #174 で解消済み**。現行 `delPlayer` 実行後の残留参照は**実測ゼロ**（テストデータ6パターン・state 全体の深走査で確認。§2.2）。
2. **残っているのは、より大きい方の半分**＝「**削除という操作そのものが、過去コンペの結果を黙って書き換える**」こと。実測で**グロス対抗の優勝チームが入れ替わり**（4名326 → 3名247 で3位→優勝）、**賞金ポイント総量が 108 → 81 に減り**、**全員の配当額が変わる**（§3）。これは #185 §0 で禁じた振る舞いそのもの。
3. よって PR3 の主眼は掃除の追加ではなく **「削除しない選択肢（退会フラグ `player.retired`）を既定にする」**。退会は**計算に1バイトも触れない**（回帰22ケース全一致を実測済み・§9）。物理削除は「参加履歴0件の選手」に限定し、記録ごとの完全削除は幹事メニューへ隔離する。

## 2. 実測1 — 選手ID を保持する全フィールドと、掃除しなかった場合の挙動

### 2.1 計測方法

`tools/regress.mjs` と同じ vm ハーネス（`scratchpad/delref.mjs`）で `js/*.js` を全ファイル読み込み、アプリ内テストデータ6パターン（`SD_PATTERNS` p1〜p6）を生成。**`state` 全体を深走査して、対象選手IDが「値」または「キー」として現れる JSON パスを列挙**した（推測ではなく構造走査）。アプリのコードは1バイトも変更していない。

### 3.2 次回幹事も変わりうる（p1・個人戦フル）

削除前 `["2qplzdo","hvronxr","7g2d920"]` → 削除後 `["2qplzdo","hvronxr","cdmkbxe"]`。**ブービー賞の該当者が入れ替わった**（削除された選手のネットが抜けて順位が繰り上がるため）。同時に賞金ポイント総量 44 → 42、配当も全員変化（例: 6,000円 → 6,286円）。

### 3.3 平均モード（#185 後の既定）でも変わる

p2（`teamScoreMode='avg'`・4名チーム）で1名削除: グロス対抗 **91.5 → 102**、ネット対抗 **71.4 → 75.2**（勝者もレッド → ブルーに反転）。**平均化は人数差の不公平を消すが、「メンバーが消えると平均自体が動く」ことは消せない。**

### 3.4 合計モード（既存コンペ）は影響がさらに大きい

p6（`teamScoreMode='sum'`・2名チーム）で1名削除: グロス対抗 **180 → 90**（1名合計）。勝者がブルー → レッドに反転。**「人数の少ないチームが自動的に有利」という #171 の元の実害が、削除操作によって再生産される。**

### 3.5 まとめ: 掃除しても掃除しなくても過去は変わる

| 方式 | 過去コンペの結果 | 記録の復元 | 表示 |
|---|---|---|---|
| 掃除しない（#174 以前） | **変わる**（しかも誤った値。§2.4） | 可（IDは残る） | 幽霊行・「?」表示 |
| 全部掃除する（現行） | **変わる**（正しい値だが別物） | **不可** | 破綻なし |
| **退会フラグ（本設計）** | **変わらない（1ビットも）** | 可（何も消さない） | 破綻なし |

## 4. 方針決定

### 4.1 #185 §0 原則との整合

#185 §0 は「**既存ゲームは `sum` のまま＝過去コンペの値・勝者・配分は1打も変わらない**」を確立し、`migrate()` での救済補完すら禁じている（既存ゲームに新既定を適用しない）。§3 の実測が示すとおり、**選手の物理削除は migrate の比ではない規模で過去を書き換える**（優勝チーム反転・配当総額 108→81）。したがって:

- **D-1（確定）**: `migrate()` で参照切れを自動掃除しない（現行方針の追認）。起動しただけで過去の結果が変わってはならない。点検・修復は今までどおり幹事の明示操作（データ点検パネル）でのみ行う。
- **D-2（確定）**: **既定の操作を「削除」から「退会」に変える**。過去の記録に触れずにマスタの見た目だけを整理できる手段を用意し、物理削除は例外扱いにする。

### 4.2 案の比較

| 案 | 内容 | 過去の保全 | 実装コスト | 判定 |
|---|---|---|---|---|
| A | 現状維持（全掃除＋件数つき確認ダイアログ） | ✗ 変わる・復元不可 | 0 | ✗ #185 §0 と矛盾 |
| B | **退会フラグ `player.retired`**（マスタからは隠すが `state.players` には残す） | **◎ 不変（実測）** | **小**（`calc.js` 非接触・UI 2箇所・1フィールド） | **◎ 採用** |
| C | 各ゲームに選手名のスナップショットを複製（`g.playerSnap`）して物理削除を許す | △（エブリ/性別/生年月日まで複製しないと `evPer`/タイブレークが狂う＝実質 players の丸複製） | 大（`calc.js` の `state.players.find` 8箇所＋`§3` の解決経路を全部差し替え） | ✗ 効果は B と同じで回帰リスクだけ大 |
| D | 参加履歴のある選手は削除不可（ボタンを出さない） | ◎ | 小 | **◎ B と併用して採用** |
| E | `migrate()` で参照切れを自動掃除 | ✗ 起動で過去が変わる | 小 | ✗ 明示的に不採用（D-1） |

**採用 = B + D**。加えて、記録ごとの完全削除（＝現行 `delPlayer` の挙動）は**消さずに残す**が、幹事メニュー配下（データ点検の隣）へ移し、退会者だけを対象にする。**「取り返しのつかない操作は2枚のドアの奥に置く」**という #177A（一括削除を作らない）の方針と同型。

### 4.3 「退会」の意味論（確定事項）

- 退会者は **`state.players` に残り続ける**。したがって `teamMembers` / `evPer` / `uvHdcpA` / タイブレーク等の**すべての計算・表示が従来どおり**動く（**退会は計算から一切見えない**）。
- 退会者は **新しいコンペの参加者候補チップに出ない**。ただし **すでに `participants` に入っている退会者はチップに出す**（過去コンペを開いたときに外せない／状態が見えないのを防ぐ。タグ「退会」つき）。
- 退会は**いつでも復帰可能**（`retired=false` に戻すだけ）。
- 退会者も次回幹事の候補になり得る（過去コンペを開いて計算した場合）。**計算に条件を足さない**ことを優先する（§3 は load-bearing）。→ PM 確認 Q7。

## 5. データモデル（§4 追補）

```jsonc
"players": [ { "id":"xxx", "name":"山田", "gender":"M", "birth":"1975-04-12",
               "everyType":"none", "kanjiExempt":false,
               "retired": false } ]   // ★2026-09-13 追加。true=退会（マスタ一覧と参加者候補から隠すだけ）
```

- **`migrate()` に1行**: `if(p.retired===undefined) p.retired=false;`（既存 `kanjiExempt` と同じ位置・同じ型の backfill）。
- **`addPlayer()`** は `retired:false` を明示して push（`newGame()` が既定値を明示しているのと同じ流儀）。
- **localStorage キーは5つのまま**（`golfCompe_v1` / `golfCompe_lang` / `golfCompe_theme` / `golfCompe_channel` / `golfCompe_seenTop`）。退会者一覧の開閉トグルは**揮発**（モジュールスコープ `let plShowRetired=false;`。`sdPat` / `auditRan` と同じ流儀）。
- **バックアップ互換**: `importData()` は `migrate(s)` を通る（`js/backup.js:6`）ので、`retired` を持たない旧 JSON も自動で `false` 補完。新 JSON を旧版アプリで開いても `retired` は無視されるだけ（前方互換）。
- **`§3` の計算仕様は非接触**（`js/calc.js` は1行も変更しない）。

**正本への追補（本PRで docs 側に入れる。`2026-07-12-golf-compe-web.md` §4）**:
> ★2026-09-13 追補【確定】（`docs/handoff/2026-09-13-player-delete-refs.md` が正）: `players[]` に `retired`(bool・既定 false) を追加。**true＝退会**で、マスタ一覧と「参加者」候補チップから隠すためだけのフラグ。**§3 の計算（`teamMembers`／`evPer`／タイブレーク／次回幹事ほか）は `retired` を一切参照しない**＝退会させても過去コンペの値・勝者・配分は1ビットも変わらない（回帰22ケース完全一致で実証）。`migrate()` が未定義を false で補完。

## 9. 既存19→22ケースの期待値は動くか → **動かない（実測）**

`tools/regress.mjs` のコピーに `PLAYERS` へ `retired` を付与（1人おきに `true`）して既存 `tools/regress-expected.json` と比較した結果:
