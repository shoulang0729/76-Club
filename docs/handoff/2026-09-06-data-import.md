## 1. 前提の確認（実装者が最初に読む）

- 76-Club は**バックエンドを持たない静的サイト**（GitHub Pages・`index.html` ＋ 素の `<script src>` 順次読込）。**本書の項目1・2・4は外部通信を一切しない**（`fetch` を書かない）。項目3の自動読取だけが外部 API を要求するが、それは §7 で**不採用**とした。
- 全データは `localStorage['golfCompe_v1']`（`state`）。**新規キーを作らない**。取込の一時状態（textarea の中身・プレビュー・Undo スナップショット）は**すべて module 変数＝揮発**。
- **ESM 化しない**。`js/import.js` はトップレベルに `const`（純データ）と `function` 宣言だけを置き、inline `onclick`/`onchange` から呼ぶ（既存方式）。
- 読込順（`index.html`）への挿入位置: **`js/score.js` の直後・`js/testdata.js` の直前**。
  ```
  state → i18n → nav → home → basic → players → game → course → score → ★import → testdata → calc → results → results-team → results-m1 → roulette → backup → init
  ```

  実際には `import.js` はトップレベルで他モジュールを参照しない（`t()`/`save()`/`uid()`/`toast()`/`state` はすべて**呼び出し時**に解決）ので読込順に非依存だが、レビューの読み順を素直にするため上記に固定する。`?v=` は PR 番号に一括更新（CLAUDE.md）。

### 2.2 モジュール構成（`js/import.js`）

```
/* ---- 0) 揮発状態 ---- */
let impPrev = null;      // 直近のプレビュー結果 {kind:'score'|'roster'|'course', rows:[...], ok:n, ng:n}
let impUndo = null;      // {snap:<state のディープコピー JSON文字列>, tab:'score'|'players'|'course', n:件数}
let impHalf = 'out';     // 項目1「9個入力時の区間」セレクタ（'out'|'in'）

/* ---- 1) 共通ユーティリティ ---- */
impNorm(s)          // 全角→半角（数字・英字・スペース）・タブ/カンマ→スペース・連続スペース1つ・trim
impTokens(line)     // 区切り判定（タブ>カンマ>スペース）してトークン配列に
impIsNum(tok)       // /^-?\d+$/
impSplitNameNums(t) // 右端から数値トークンを剥がし、残りを名前として返す → {name, nums:[]}
impKey(name)        // 名前照合キー: impNorm → 小文字化 → 空白を全除去
impCsvLine(line)    // RFC4180 の最小サブセット（"" エスケープ・囲みクォート。フィールド内改行は非対応）

/* ---- 2) パーサ（純関数・DOM も state も触らない＝テスト可能） ---- */
impParseScores(text, half, ctx)   // → rows[]
impParseRoster(text, ctx)         // → rows[]
impParseCourse(text)              // → rows[]

/* ---- 3) UI（各タブから呼ばれる） ---- */
impPanel(kind, g)     // <details> の HTML を返す（renderScore/renderPlayers/renderCourse から埋め込む）
impDoPreview(kind)    // textarea を読み parse → #impPrev だけ innerHTML 差し替え（textarea は再描画しない）
impApply(kind)        // Undo スナップショット取得 → 反映 → save() → 該当 render*() → toast
impUndoApply()        // スナップショット復元 → save() → render()
impClear(kind)        // textarea と プレビューをクリア
```

**設計上の要点**:
- **パーサは純関数**（引数 `ctx` に候補選手名リスト等を渡す）。DOM と `state` に触らないので、将来 `tools/` にテストを足せる。
- **プレビューは「プレビュー」ボタン押下で生成し、差し替えるのは `#impPrev` だけ**。textarea を innerHTML 再描画すると**入力中のフォーカスとカーソル位置が飛ぶ**（`js/score.js` の `setScore` が「再描画せず合計セルだけ更新」しているのと同じ理由）。`oninput` でのライブプレビューは採用しない。
- 各タブの render は**1行**だけ増える。例（`js/score.js`）:
  ```
  html += impPanel('score', g);
  ```

### 2.3 パース失敗時の扱い

**2段（プレビュー→確定）＋部分成功を許す。**

1. 「プレビュー」を押すと `#impPrev` に**行ごとの表**が出る。列は `行 / 状態 / 名前 / 内容`。
2. 状態は 4 種:
   - **新規**（`imp.new`・緑系タグ ＝ 既存機能色の「勝ち=緑」は使わない。ニュートラルな `tag` を使う）
   - **更新**（`imp.update`）／**上書き**（`imp.overwrite`・既存スコアを書き換える行）
   - **エラー**（`imp.err`・赤 `var(--red)`）＝ その行だけスキップ。理由を「内容」列に日本語で出す。
3. エラー行が1件以上あれば表の下に `imp.errHead`（`{n}行にエラーがあります（その行だけスキップします）`）。
4. 確定ボタンの文言は `imp.applyN`（`{n}件を取り込む`）。`n=0` なら**ボタンを disabled** にして `imp.none` を出す。
5. **全部やり直しにはしない**理由: 幹事が読み上げながら20行打った最後の1行のタイプミスで全部捨てるのは現場運用に耐えない。ただし「気づかず部分取込された」を避けるため、**エラー件数は確定前に必ず見える**（=2段にする意味）。

**「プレビューせずに確定」はできない**（確定ボタンはプレビュー後にのみ描画される）。

### 2.4 既存データとの突き合わせ

**参考にした現行ロジック**（`js/testdata.js:186-193`）:

```
/* 選手マスターは同名なら再利用して属性を上書き（現行ロジック踏襲＝再生成しても選手が増えない・D5） */
function sdPlayer(spec){
  let p=state.players.find(x=>x.name===spec.name);
  if(!p){ p={id:uid(),name:...,gender:...,birth:...,everyType:...,kanjiExempt:...}; state.players.push(p); }
  else { p.gender=spec.gender; p.birth=spec.birth; p.everyType=spec.everyType; p.kanjiExempt=spec.kanjiExempt; }
  return p.id;
}
```

**本件の方針（testdata との違いを明記）**:

| 論点 | testdata（現行） | 本件（取込） | 理由 |
|---|---|---|---|
| 同名判定 | `x.name===spec.name`（**厳密一致**） | `impKey(x.name)===impKey(row.name)`（**正規化一致**: 全角/半角・大小文字・空白の有無を無視） | 「田中 太郎」と「田中太郎」を別人にしない。Excel/LINE からのコピペで空白がゆれる |
| 属性の上書き | **全属性を無条件に上書き** | **入力に列が存在する項目だけ上書き** | 氏名だけの名簿を貼って `birth` が全消しになるのを防ぐ |
| 同名が複数 | 先頭を採用 | **エラー**（`imp.e.ambiguous`）＝その行はスキップ | 誤って別人を書き換えるほうが害が大きい |
| 新規 | 追加 | 追加（`uid()` で採番。既定 `gender:'M'`・`birth:null`・`everyType:'none'`・`kanjiExempt:false`） | `state.players[]` のスキーマそのまま |

**項目1（スコア）の照合先**は `state.players` ではなく **`g.participants`（現ゲームの参加者）**。手順:
1. `g.participants` の各 pid → `state.players` の名前 → `impKey` で候補表を作る。
2. 完全一致（`impKey` 同士）1件 → 確定。
3. 0件で、かつ `state.players` には居る → **エラー `imp.e.notPart`**（理由文に「選手・チームタブで参加者に追加してください」）。
4. 0件でどこにも居ない → **エラー `imp.e.noPlayer`**。
5. 2件以上 → **エラー `imp.e.ambiguous`**。

→ **スコア取込は `g.participants` を書き換えない**（＝「参加者の自動追加」はしない）。未決事項 §12-② に上げる。

### 2.5 取り消し（Undo）

**1段の揮発 Undo。**

```
impApply(kind){
  impUndo = { snap: JSON.stringify(state), tab: activeTab, n: 取込件数 };
  ...反映...
  save(); render該当(); toast(t('imp.done',{n,s}));
}
impUndoApply(){ state = JSON.parse(impUndo.snap); impUndo=null; save(); render(); toast(t('imp.undone')); }
```

- **`localStorage` には一切書かない**（キーを増やさない）。ページをリロードすると失効する。
- **`impUndo.tab !== activeTab` なら「元に戻す」ボタンを描画しない**（＝タブを移動したら取り消せない）。`nav.js` の `go()` には触らずに実現できる（`import.js` が `activeTab` を読むだけ）。
- 注意文 `imp.undoNote`: 「**取込後に加えた編集も失われます。タブを移動すると取り消せなくなります。**」を必ずボタンの横に出す。
- `state` 全体のスナップショットなので**サイズは JSON で数十KB**（30名×18ホールでも十分小さい）。メモリ懸念なし。
- 2回目の取込で 1回目のスナップショットは**上書き**（Undo は常に1段）。

**なぜ差分 Undo にしないか**: 差分（どの pid のどのホールを何から何に変えたか）を持つと、名簿取込の「チーム新規作成」「参加者追加」まで正確に巻き戻す実装が増える。全スナップショット方式なら**1行で確実**。トレードオフ（取込後の編集も消える）は注意文で明示する。

## 3. 項目1: スコアの一括入力（ペースト）★最優先

> `docs/handoff/2026-08-31-host-excel-analysis.md` §3.3 の幹事Excel `input help` シート（`名前 3 3 4 …` を `FIND`/`MID`/`VALUE` で18列に分解）＋ §10 候補 **D**（推奨★★★）に相当。**幹事Excel で実際に使われている運用**なので、フォーマットはそれに寄せる。

### 3.1 入力フォーマット仕様

**1行 = 1選手**。空行は無視。行頭 `#` はコメントとして無視。

```
<名前> <数値> <数値> … <数値>
```

#### (a) 正規化（`impNorm`）
処理順に:
1. 全角数字 `０-９` → 半角 `0-9`
2. 全角英字 `Ａ-Ｚａ-ｚ` → 半角
3. 全角スペース `U+3000` → 半角スペース
4. **タブ・カンマ → 半角スペース**
5. 連続スペース → 1つ
6. `trim`

→ **区切り文字はスペース／タブ／カンマのいずれでもよい**（Excel からのコピペはタブ、CSV はカンマ、読み上げ打ちはスペース）。

#### (b) 名前と数値の切り分け（`impSplitNameNums`）

**行末から数値トークンを剥がし、残りの先頭部分を「名前」とする。**

- 幹事Excel の `input help` は `FIND(" ")` で**最初のスペースまで**を名前にしている＝**「田中 太郎」のように姓名の間にスペースがある名前で壊れる**。76-Club の選手名は姓名の間にスペースがある想定（`js/testdata.js` の `'田中 太郎'`）なので、**右から剥がす方式に変える**。
- 数値トークンの定義: `/^\d{1,2}$/`（1〜2桁の整数）。または**空欄マーカー** `-` / `_` / `.` / `*`。
- 剥がした結果、名前が空 → エラー `imp.e.noName`。

| 入力行 | 名前 | 数値トークン数 |
|---|---|---|
| `田中 太郎 4 5 3 4 5 4 4 3 4 4 4 3 4 5 4 4 3 4` | `田中 太郎` | 18 |
| `田中太郎,4,5,3,…` | `田中太郎` | 18 |
| `田中 太郎<TAB>4<TAB>5<TAB>…` | `田中 太郎` | 18 |

**既知の制限**（設計として受け入れる・注記に書く）: **名前そのものが1〜2桁の数字だけの選手**（例: 名前が `3`）は正しく切り分けられない。実運用で発生しないため許容。

#### (c) 数値トークン数と割り当て

| 個数 | 解釈 | 検算 |
|---|---|---|
| **18** | 1H〜18H そのまま | なし |
| **19** | 18H ＋ 末尾に**合計** | `t[18] === Σt[0..17]` を検算。合わなければ `imp.e.sub` |
| **20** | 9H ＋ **OUT小計** ＋ 9H ＋ **IN小計**（index 9 と 19 が小計） | `t[9]===Σt[0..8]` かつ `t[19]===Σt[10..18]`。合わなければ `imp.e.sub` |
| **21** | 上記 20 ＋ 末尾に**合計** | 20 の検算 ＋ `t[20]===t[9]+t[19]` |
| **9** | **ハーフのみ**。パネルの「9個入力時の区間」セレクタに従い 1-9H または 10-18H | なし |
| **10** | 9H ＋ **小計** | `t[9]===Σt[0..8]` |
| それ以外 | エラー `imp.e.count`（`数字の個数が合いません（{n}個）`） | — |

**空欄マーカーが含まれる行では小計の検算をスキップし、個数だけで判定する**（合計値が計算できないため）。

#### (d) 値の妥当性

- 許容範囲は **1〜15**（`js/score.js` の `<input type="number" min="1" max="15">` と一致させる）。
- 範囲外（`0` を含む）が1つでもあれば**その行全体をエラー** `imp.e.range`。セル単位のスキップにはしない（1人分のカードは一体なので、部分的に入るほうが危険）。

#### (e) 空欄の扱い

- **空欄マーカー `-` `_` `.` `*` は「その ホールは触らない（既存値を維持）」**。`null` で上書きして既存値を消すことは**しない**。
- **9個モードは指定した区間だけを書く**。反対のハーフは触らない。
- → **前半だけ先に貼り、後半を後から貼る**運用が安全に成立する。

### 3.4 読み上げ運用への耐性（現場チェック）

想定運用: 幹事がスコアカードの束を見ながら、1人ずつ読み上げて打つ。

| 現場の要求 | 本設計の対応 |
|---|---|
| 1人打ったらすぐ確定したい | textarea が1行でもプレビュー→確定できる。確定後 **textarea は自動でクリア**され、次の1人をすぐ打てる |
| 打ち間違えたら戻したい | 揮発 Undo 1段（§2.5）。加えて、確定前のプレビューで「上書き◯」件数が見える |
| 前半だけ先に集めた | 9個モード＋区間セレクタ（§3.1c） |
| カードに OUT/IN 小計が印字されている | 20個/21個パターンを**検算つきで**自動除去（§3.1c）。**検算が通ることが打ち間違いの検出になる**（幹事Excel には無い利点） |
| 途中のホールが空欄 | `-` マーカーで飛ばせる。既存値を消さない |
| 全角で打ってしまった | `impNorm` が全角数字・全角スペースを吸収 |
| 名前が「田中 太郎」 | 右から数値を剥がす方式（§3.1b）。幹事Excel の `FIND(" ")` 方式より堅い |
| iPad で打つ | textarea は `inputmode` 指定なし（名前も打つため）。数字キーパッドは既存のホール表を使う |

**結論: 耐える。** むしろ小計検算があるぶん幹事Excel より安全。

## 4. 項目2: 選手名簿の取込（CSV / 貼付）

### 4.1 `state.players[]` のスキーマ（`js/state.js` 実測）

`newGame`/`migrate`/`addPlayer` から確定した現行スキーマ:

| フィールド | 型 | 既定値 | 取込での必須/任意 | 備考 |
|---|---|---|---|---|
| `id` | `string` | `uid()` | **自動**（入力しない） | 7文字の乱英数 |
| `name` | `string` | — | **必須** | 空ならエラー `imp.e.noName` |
| `gender` | `'M'` \| `'F'` | `'M'` | 任意 | `migrate` で `undefined→'M'` |
| `birth` | `'YYYY-MM-DD'` \| `null` | `null` | 任意 | 同ネットのタイブレークに使用 |
| `everyType` | `'none'` \| `'every1'` \| `'every2'` | `'none'` | 任意 | エブリ区分（§3 計算の入力だが、**値の意味は変えない**） |
| `kanjiExempt` | `boolean` | `false` | 任意 | 次回幹事の対象外フラグ |

**フィールドの追加・削除・型変更はしない。**

### 4.2 列の並びの決め方

**ヘッダ行があればヘッダで判定、無ければ固定順。**

1. 1行目をトークン分割し、**いずれかのセルが既知のヘッダ語に一致すれば「ヘッダ行」**とみなして列マップを作り、その行はデータとして扱わない。
2. ヘッダ行が無ければ**固定順**を使う:
   ```
   氏名, 性別, 生年月日, エブリ区分, チーム, 幹事対象外
   ```
   列数が足りない行は「その列は入力に存在しない」＝**既存値を維持**（新規なら既定値）。

**ヘッダ語の別名表**（`impNorm` → 小文字化 → 空白除去 後の完全一致）:

| フィールド | ja | zh | en |
|---|---|---|---|
| `name` | 氏名 / 名前 / 選手 / 選手名 | 姓名 / 名字 / 选手 | name / player |
| `gender` | 性別 / 性 | 性别 | gender / sex |
| `birth` | 生年月日 / 誕生日 / 生日 | 出生日期 / 生日 | birth / birthday / dob |
| `everyType` | エブリ / エブリ区分 / hdcp区分 / ハンデ | 让杆 / 让分 | every / hdcp / handicap |
| `team` | チーム / 組 / 所属 | 队 / 队伍 / 组 | team |
| `kanjiExempt` | 幹事対象外 / 幹事除外 / 対象外 | 干事除外 | exempt / kanjiexempt |

**未知のヘッダ語の列は無視**（プレビューの注記で「◯列を無視しました」とは出さない＝ノイズ。単に使わない）。

### 4.3 区切りの判定（`impTokens`）

1行目を見て:
1. タブが1つ以上 → **タブ区切り**（Excel からの貼付）
2. なければカンマが1つ以上 → **カンマ区切り**（CSV）。この場合のみ `impCsvLine` で **RFC4180 の最小サブセット**（`"` 囲み・`""` エスケープ）を解釈。**フィールド内の改行は非対応**（1行1レコード）。
3. どちらも無ければ **空白区切り**

**ファイル読込も可**: `<input type="file" accept=".csv,text/csv,text/plain">` で `FileReader.readAsText`（`js/backup.js:importData` と同じ手口）。**文字コードは UTF-8 のみ**（Shift_JIS は非対応。Excel の「CSV UTF-8」で保存してもらう。注記に書く）。BOM は先頭で除去。

### 4.4 表記ゆれの吸収範囲

すべて `impNorm` → 小文字化 → 空白除去 後に判定。

**性別 `gender`**

### 4.5 チーム所属の同時投入

**できる。** チーム列があるとき（現ゲームが選択されている場合のみ有効）:

1. チーム名が `g.teams` に**既存**（名前の `impKey` 一致）→ そのチームに追加。
2. **無ければ新規作成**: `g.teams.push({id:uid(), name:<入力の表記そのまま>, memberIds:[], color:tmPickColor(g,name)})`
   - `tmPickColor` は `js/players.js` の既存関数（重複回避の自動割当・`2026-08-30-team-colors.md` §14）を**そのまま再利用**。新規の色ロジックは書かない。
3. メンバー追加は `toggleTeamMember` と同じ**排他ルール**（他チームから外してから追加）。
4. **チーム列に値がある行は `g.participants` にも自動追加**（チーム所属は参加者であることが前提）。

## 6. 項目3: スコアカードの写真取込 — 実現性の評価

> **結論を先に書く: 2026年時点で、ブラウザだけ（バックエンドなし）で紙のスコアカードの手書き数字を実用精度で読むのは現実的でない。** 自動読取は **不採用**とし、段階0（運用ガイド）・段階1（写真を見ながら入力するビュー）で価値を出す。

### 6.1 選択肢の比較

| 案 | 仕組み | オフライン | 精度（手書き数字） | 追加コスト | プライバシー | 判定 |
|---|---|---|---|---|---|---|
| **(a) 外部 OCR/Vision API**（Google Cloud Vision / Azure / LLM の vision） | 写真を第三者サーバに送って結果を受け取る | **✕ 壊れる** | **最良**（実用レベル） | 実装は軽い。ただし**課金** | **✕ 参加者の氏名入りスコアカード写真が第三者に渡る**。参加者への説明・同意が必要 | **不採用**（§6.2） |
| **(b) Tesseract.js（WASM）をバンドル** | OCR エンジンを丸ごと配信 | ○ | **✕ 実用外**。Tesseract は**手書きを対象外**と公式に位置づけており、手書きは Google Cloud Vision / AWS Textract 等の専用モデルを使えと案内されている | 配信物が数MB（core wasm ＋ 言語データ）増える。GitHub Pages には置けるが初回ロードが重い | ○（端末内完結） | **不採用** |
| **(c) 自前の小型 CNN（MNIST 級）を ONNX Runtime Web / TF.js で実行** | セルを切り出して1桁ずつ推論 | ○ | **✕ 期待できない**（§6.3） | **L+**。モデル自体は小さい（MNIST 級で数百KB）が、**罫線検出・傾き補正・セル分割**が本体の難所で、実質 OpenCV.js（数MB）が要る | ○ | **見送り** |
| **(d) ブラウザ内蔵 API（Shape Detection の `TextDetector`）** | OS のテキスト検出を呼ぶ | ○ | **✕ 使えない**。Chrome/Edge のみ＋実験フラグ必須、WICG 段階で標準化されておらず、**テキスト領域を検出するだけで文字列は取り出せない** | 小 | ○ | **不採用** |
| **(e) 写真を見ながら手入力を助けるビュー**（段階1） | 写真を画面上部に固定表示し、その下で §3 の一括貼付／既存のホール表に打つ | ○ | — | **M** | ○（`URL.createObjectURL` の揮発。**保存しない**） | **採用（段階1）** |
| **(f) 端末OS の文字認識に委ねる**（段階0） | iOS「テキスト認識表示（Live Text）」/ Android「Google レンズ」で写真中の数字を選択→コピー→76-Club の一括貼付に貼る | ○（OS 機能） | OS 依存だが**印字・丁寧な手書きなら実用**。認識できなければ手入力に落ちるだけ | **ほぼゼロ**（i18n 1キーの案内文） | ○ | **採用（段階0）** |

### 6.2 (a) 外部 API を採らない理由（設計制約としての明記）

1. **オフラインで動く性質が壊れる。** ゴルフ場のクラブハウスは電波が弱いことが多く、76-Club は「静的サイト＋localStorage で通信不要」がそもそもの強み。取込のためだけに通信必須の経路を作るのは筋が悪い。
2. **API キーを置く場所がない。** 静的サイトにキーを埋めれば公開＝第三者に課金される。「ユーザーが自分のキーを入力する」案は、保管先が `localStorage`（**キーを増やせない**）か `golfCompe_v1`（**バックアップ JSON に秘密が入り、JSON を人に渡せなくなる**）しかなく、どちらも詰む。
3. **プライバシー。** スコアカードには参加者の氏名・スコアが載る。第三者サーバに送るなら参加者への説明が要る。趣味のコンペアプリが背負うには重い。
4. **代替案**（採るならこれ）: 幹事が**自分のスマホの好きなアプリ**（OS の文字認識・市販のスコアカードスキャナ）で数字を読み取り、その結果を **§3 の一括貼付に貼る**。76-Club 側の実装ゼロで、責任分界も自然。→ **これが段階0**。

### 6.3 (c) の精度が期待できない理由（推測でなく構造的な理由）

- MNIST 級のモデルは「**白背景・中央寄せ・1桁・単独**」を前提に学習されている。実際の紙スコアカードは:
  - **1〜2桁**（`10` `11` が普通に出る）→ 桁分割が別問題として発生
  - **鉛筆で罫線にかぶる**／消しゴム跡が残る
  - **記号併記**（バーディに ○、ボギーに △ を重ねる慣習）→ 数字と記号が重なる
  - **傾き・影・光の反射**（クラブハウスの照明下でスマホ撮影）
- したがって「モデルが小さいから実現できる」は**成立しない**。難所は推論ではなく**前処理（罫線検出→傾き補正→セル分割）**で、そこは実質 OpenCV.js が要る＝配信物が数MB、実装は L+。
- **市販の専用アプリ（サーバ側 AI 利用）ですら**「うまくスキャンできず全ホール手で直した」という利用者レビューが 2025 年12月時点で出ている。**バックエンドを持つ専業アプリでも完全ではない**領域に、静的サイトで挑むべきではない。

## 8. 項目4: コース情報の取込

### 8.1 入力形式

**1コース1行**。

```
<コース名> <par×18>
```

- 区切り・正規化・小計除去は **§3 と完全に共通のロジックを使う**（`impNorm` / `impTokens` / `impSplitNameNums` / 小計検算）。
- 数値トークン数の解釈は §3.1(c) と同じ表（18 / 19 / 20 / 21 を受け付ける。**9 と 10 は受け付けない**＝コースは18ホール前提）。

- **コース名は省略可**（数値だけの行）。その場合はパネルの「コース名」入力欄の値を使い、それも空なら `imp.e.noName`。
- 空欄マーカー（`-`）は**受け付けない**（par の未定義はありえない）→ `imp.e.par`。

**取り込まないもの**:
- **`g.hidden`（隠し12H）は取込対象外。** 隠しホールは「コースの属性」ではなく「そのコンペごとの抽選結果」（`randomHidden`/`pickHidden12`）。混ぜると意味論が壊れる。
- **NP/DC 対象ホールも取込対象外。** `niapinHolesOf`/`draconHolesOf` が `par` から自動導出する（`js/state.js:72-73`・`2026-08-20-npdc-par.md`）ので、**par を入れれば自動で決まる**。

## 12. 未決事項（着手前にユーザー確認が要るもの）

| # | 論点 | 既定案（確認が取れなければこれで進める） | 確認したい理由 |

| **①** | **名簿取込で、同名判定が当たったとき `name` の表記を上書きするか** | **上書きしない**（既存表記を尊重。更新するのは他の属性だけ） | 「田中太郎」で登録済みのところに「田中 太郎」を貼ったとき、表記を揃えたい人と、既存を守りたい人で流派が分かれる。上書きすると結果画面の表示名が変わるので影響が見える |
