## 3. (A) 総合タブの集約表示

### 3.1 「全連携結果」の定義【決定】

**`events[].on === true`（＝`g.announced[key]` が真）の種目だけを "結果" として見せる。** 未連携の種目は**現行どおり行ごと `？` マスク**（`js/results-team.js:107`）。

- 理由: `announced` は幹事が「この種目はもう発表した」と宣言したフラグであり、**表彰式のネタバレ防止の唯一のゲート**（winpoints-reveal D6）。ここを緩めると、パーティー中に総合タブを投影した瞬間に未発表種目の勝者が漏れる。
- 採用中（`chFormats`）だが未成立の種目は、現行どおり `events` に載らない＝**行が出ない**（`add()` の `live<2` ガード）。この挙動も変えない。
- **`？` マスクは実値にも及ぶ**（マスクセルは値も勝ち点も一切描かない）。実値だけ先に見えると勝者が確定してしまうため、ここは load-bearing。

### 3.2 何を出すか【決定】

**新しいカードを増やさず、②種目別勝ち点表のセルを「実値（大）＋勝ち点（小）」の1行に拡張する。**

```
現行セル:   [ 1 ]      （勝ちチームのみ。負けチームは空欄）
新セル:     [ 340 +1 ] （勝ち＝緑地・実値＋獲得勝ち点）
            [ 352 ]    （負け＝実値のみ・地色なし）
            [ — ]      （対象外＝現行どおり）
            [ ？ ]     （未連携行＝現行どおり・値も隠す）
```

- **①ヒーロー（総合順位・勝ち点合計）は一切変更しない。** ②の変更も「セルの中身」だけで、行順（`TP_EV_ORDER`）・列（チーム）・勝ち/山分けの色分けは不変。
- **各種目タブとの重複にならない理由**: 各種目タブが持つのは「ホール別・選手別の内訳」（スコア表・UP差の推移・NP/DC のホール別カード）。総合に出すのは**その種目の結論値1つ**だけ。粒度が違うので重複しない。
- 単位は**言語非依存のリテラル略号**を使う（既存の `NP`/`DC`/`G`/`OUT`/`IN` と同じ規律＝**i18n キー追加ゼロ**）:

| key | 表示例 | 書式 |
|---|---|---|
| `teamGross` / `teamNet` / `best2ball` / `customMatch` | `340` / `305.6` | 数値のみ（`Math.round(v*10)/10`。整数は小数点なし） |
| `holeByHole` / `vegas` / `roulette` | `12`＋small `H` | ホール数（`.rl-st-h small` と同じ表現） |
| `match1v1` | `3`＋small `W` | マッチ勝利数 |
| `univMatch` | small `#`＋`1` | 順位（1が最良。平均ネット等の明細は大学対抗タブ） |
| `niadora` | `3` | 本数（ニアドラタブのヒーローと同じ＝数字のみ） |

> `H` はルーレット／HBH の既存表示（`.rl-st-h small`）で既に「ホール数」の意味で使われている（`styles.css:367`）。HDCP は表側で `HD`（`col.hd`）なので衝突しない。

### 3.3 個人の情報を入れるか【決定＝入れない（既定案・§5 Q1 で確認）】

**総合タブにも共有画像にも、個人名・個人成績・賞金額を入れない。**

理由:
1. 総合タブはチーム戦の枠。個人の上位・賞金配分は「配分」タブ（`renderStanding`）が正で、そこに**チーム別合計表**もすでにある（`js/results.js:118`）。総合に写すと正が2つになる。
2. 投影面積（§3.5 の高さ計算）。ニアドラ勝者4人＋個人トップ3を足すと、6種目構成で iPhone の1画面に**確実に収まらなくなる**＝(B) の前提が壊れる。
3. **プライバシー**（§6）。共有画像に個人名が載らなければ、転送されても漏れるのは「チーム名と種目の数値」だけになる。
4. 横展開のほうが筋が良い: 画像基盤（`js/share.js`）ができれば、**同じ仕組みで「個人戦ネット順位の画像」「ニアドラ勝者の画像」を後から足せる**（§7 の将来拡張）。総合カードに詰め込むのは一方通行で戻せない。

### 3.5 投影原則との整合（§11.14）— 高さの実測見積り【重要】

現行 `.tp-mx` は `td{font-size:var(--f-rl-name);line-height:1;padding:2px 10px}`（`styles.css:433`）＝行高 ≒ `--f-rl-name + 4px`。

| 端末/幅 | `--f-rl-name` | 1行 | ヘッダ | ヒーロー | 見出し＋ヘッダ行＋注記＋details | **6種目のカード全高** |
|---|---|---|---|---|---|---|
| スマホ（<1024px） | 30px | 34px | 24px | 約110px | 約150px | **約 490px** |
| 投影（1024px〜） | 40px | 44px | 30px | 約150px | 約170px | **約 614px** |
| 投影（1366px〜） | 48px | 52px | 34px | 約170px | 約180px | **約 696px** |

**実値を併記しても行は高くならない**（値と `+1` を**同じ1行**に置くため）。これが「集約しても投影で読める大きさを維持できる」ことの根拠。

**ただし横は増える。** 値セルは現行「1文字」→「最大5文字（`305.6`）＋`+1`」になるため、狭幅×多チームで破綻する。対策:

- **`teams.length >= 4` のとき `.tp-mx` に `.tp-mx-d`（dense）を付ける**＝値 `calc(var(--f-rl-name)*.72)`・ヘッダ/種目ラベル `calc(var(--f-rl-name)*.48)`。**新規 CSS 変数（トークン）は追加しない**（既存 `--f-rl-name` の係数違いのみ＝`@media` 再定義に自動追従）。
- 3チーム以下は係数変更なし＝**現行と同じ大きさ**。
- 表は現行どおり `.scroll` の中なので、それでも溢れる極端なケース（チーム5＋長いチーム名）は横スクロールに落ちる＝**現行と同じ最悪系**（デグレなし）。

### 4.2 (a)（CDN）は明確に不可【決定】

**採らない。** 本アプリはコース上（電波の弱い/圏外のゴルフ場）で使う前提（CLAUDE.md・正本 §5）。CDN からの取得が失敗した瞬間に共有機能が丸ごと死ぬ。しかも失敗するのは**必ずコースの上**＝一番使いたい場所。加えて第三者 CDN への Referer 送出（コンペ名は URL に載らないが、アクセスログは残る）も、端末内 localStorage のみで完結してきた本アプリの性格に合わない。

> 補足（事実確認）: `index.html:8-10` は Google Fonts を読んでいる＝**オフライン時はすでに system フォントにフォールバックしている**。これは「読めなくなるだけ」の劣化で済むが、JS ライブラリの取得失敗は**機能の消失**になる。同列に扱わない。

### 4.3 (f)（1枚に収まるビュー＋スクショ）は足りない【決定・正面評価】

(f) は魅力的（実装ゼロ・オフライン完全・フォント完全再現）で、**ユーザーは現に既にこれをやっている**（バックログ #132「画面キャプチャして皆さんお願いします〜でした」）。しかし**足りない**。理由は5つ、いずれも具体的:

1. **`.result-sticky` が必ず写り込む。** 結果発表画面はグループタブ（個人戦/チーム戦/配分）とゲームタブ（総合/ニアドラ/…）の**2段 sticky**（`js/results.js:77-82`）。スクロールしても上に残るので、**参加者に配る画像に操作UIが必ず入る**。
2. **コンペ名とカードが同時に写る保証がない。** コンペ名は `header#hdrGame`（`index.html:17`）にあり、カードは `main` の中。カード先頭まで少しでもスクロールするとヘッダは残るがカード下端が切れ、逆も起きる。§3.4 の共有ヘッダを足せば緩和するが、下端が切れる問題は残る。
3. **縦が端末依存で切れる。** §3.5 の見積り（6種目でカード約490px）に、ヘッダ50px＋ナビ44px＋sticky 88px が乗る。iPhone SE（667px）の可視領域は約485px＝**6種目で既に溢れる**。7種目以上・4チーム以上は主要機種でも確実に2枚になる。「複数回スクショ」は**ユーザーが今不満に思っている運用そのもの**。
4. **ダークテーマ利用者の画像が黒背景になる。** チャットに貼ったときの可読性が落ち、印刷（幹事が紙で配る）もできない。テーマは `golfCompe_theme` に保存された個人設定なので「共有前にライトに切り替えて」は運用として弱い。
5. **切り抜き・向き・解像度が端末任せ。** 参加者の端末で見たときの読みやすさが幹事の端末に左右される。投影原則（後方席から読める）を共有物側で担保できない。

**→ (f) は「常に使えるフォールバック」として残す（何も禁止しない）が、要件 (B) の答えにはしない。**

### 4.4〜4.5 (b)(d)(e) を採らない理由

- **(b) 同梱**: オフラインは保てるが、`html2canvas`（最小版で約190KB・要実測）は**レビュー不能なブラックボックス**をリポジトリに常駐させる。本アプリは `js/**` 全体で約300KB＝**依存1本でコード量が6割増える**。かつ html2canvas は自前レイアウトエンジンなので、本アプリが使っている **container query（`.npdc-kind` の `23cqw`・`styles.css:245`）・`min()`・flex baseline 揃え**の再現に不安が残る（総合カードは幸い単純だが、将来他画面に横展開したときに効いてくる）。**非ESM `<script src>` で読める点（UMD）は問題にならないが、採らない。**
- **(d) SVG foreignObject**: Safari の既知バグが重い。`x`/`y`/`transform` が無視される・`width`/`height` 未指定だと**何も描画されない**・`position:absolute` の子が SVG ルートに飛ぶ・PNG 化が**数回試さないと成功しない**という報告がある（[WebKit #23113](https://bugs.webkit.org/show_bug.cgi?id=23113)・[react-d3-tree #284](https://github.com/bkrem/react-d3-tree/issues/284)・[w3tutorials](https://www.w3tutorials.net/blog/svg-foreignobject-not-working-properly-on-safari/)）。さらに**外部フォント（Google Fonts）は base64 インラインしない限り落ちる**＝日本語が別フォントになる。**幹事の運用端末が iPhone である以上、採用不可。**
- **(e) 印刷CSS→PDF**: 実装は小さそうに見えて、実際は「印刷時に sticky/nav/タブ/`<details>` を全部畳んでカードだけをA4に収める」`@media print` を書くことになり、画面を触るたびに壊れる保守負債が付く。かつ**PDF は LINE/WeChat で画像より確実に開かれない**（サムネが出ない・相手が別アプリに遷移する）。**本件では採らない。**将来「幹事が紙で配りたい」要望が出たら独立Issueで。

### 4.6 推奨 = (c) 自前 canvas 描画【決定】

#### 二重管理をどう防ぐか（設計の要）


- 受け入れ条件として「`js/share.js` に `curGame|teamWinPoints|document.getElementById|innerHTML` が現れないこと」を機械チェックにする（§8）。

### 4.7 共有・保存の経路【load-bearing・iOS の同期制約】

```js
/* ① 画像生成（ボタン onclick から直接） */
function tpShareMake(){ /* … canvas 描画 … */
  tpShareImg={ url: cv.toDataURL('image/png'), w: cv.width, h: cv.height };   // ★同期
  renderResult(); toast(t('share.done')); }

/* ② 共有/保存（ボタン onclick から直接・★全て同期＝user activation を落とさない） */
function tpShareSend(){ if(!tpShareImg) return;
  const b64=tpShareImg.url.split(',')[1], bin=atob(b64);
  const arr=new Uint8Array(bin.length); for(let i=0;i<bin.length;i++) arr[i]=bin.charCodeAt(i);
  const f=new File([arr], tpShareName(), {type:'image/png'});
  if(navigator.canShare && navigator.canShare({files:[f]})){
    navigator.share({files:[f], title:t('team.overallTitle')}).catch(()=>{});   // 中断は無視
    return; }
  const a=document.createElement('a'); a.href=tpShareImg.url; a.download=tpShareName(); a.click(); }
```

- **`canvas.toBlob()` を使わない。** `toBlob` は非同期で、`await` を挟むと iOS Safari は**一時的ユーザー活性化（transient activation）を失って共有シートを黙って出さない**（[web.dev: share files](https://web.dev/patterns/files/share-files)・[Apple Developer Forums](https://developer.apple.com/forums/thread/665812)）。`toDataURL`→`atob`→`Uint8Array`→`File` は全て同期なので活性化が保たれる。**ここは実装時に崩さない。**
- `navigator.canShare({files})` が false（Android Chrome の一部・PC）→ `<a download>`。デスクトップでは確実に動く。
- **最終フォールバック＝プレビュー常設**: 生成した画像は必ず共有パネル内に `<img src=dataURL>` で表示する。共有もダウンロードも効かない環境でも**長押し（右クリック）で保存**できる＝どの端末でも必ず持ち出せる。幹事が中身を確認してから配れる利点もある。
- **オフラインで全て成立する**: `toDataURL` も `navigator.share` もネットワークを使わない。GitHub Pages は https なので secure context 条件も満たす。

総合カードの**最下部**、既存「種目別勝ち点の配点設定」`<details>` の**直後**に、もう1つ `<details>`（既定＝閉）を置く。

```
    [画像を作成]  ← btn sm       ← share.make
    ┌───────────┐
    │ （生成画像プレビュー）  │  ← max-width:100%・角丸・枠線
    └───────────┘
    [共有・保存]  ← btn gold sm  ← share.send（生成後のみ表示）
    長押しでも保存できます。未連携の種目は ？ のまま出力されます  ← share.note
```

## 10. 触らない範囲（load-bearing）

- **`js/calc.js` は1行も変更しない。** `teamWinPoints` / `computePoints` / `computePayout` の返り値・`events[].vals` の意味・`announced` の意味論・`TP_EV_ORDER` の並びは不変。
- **`？` マスクの規律**: 未連携（`ev.on===false`）の行は、画面でも画像でも**値・勝ち点・勝者を一切描かない**。
- **localStorage キーは 5 つのまま**（`golfCompe_v1` / `golfCompe_lang` / `golfCompe_theme` / `golfCompe_channel` / `golfCompe_seenTop`）。共有パネルの開閉・生成画像は**揮発**。
- **i18n は ja/zh/en 同時追加・キー集合完全一致・未使用キー0。**
- **inline `onclick` 方式／非 ESM**（`js/share.js` も通常 `<script src>`・グローバル関数）。
- **新規 CSS トークン（カスタムプロパティ）を足さない。** 既存 `--f-rl-name` 等の係数違い・既存色トークンの参照のみ。
- **外部ネットワークに依存しない**（CDN・フォント取得・API 呼び出しを追加しない）。
