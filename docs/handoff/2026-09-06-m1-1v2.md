## 1. 背景・一般慣例の調査

- ゴルフ規則の用語では、**1名 対 2名のマッチは「ベストボール（Best-Ball）」＝「1名 vs 2名のうち良い方のスコア」**が標準的な流派（Rules of Golf の Best-Ball 定義：*"A match in which one player plays against the better ball of two other players"*）。「平均」は一般的な公式フォーマットではなく**ハウスルール**。
  - 出典: [Golf Distillery — Best Ball](https://www.golfdistillery.com/definitions/play-formats/best-ball/) / [Wikipedia — Four-ball golf](https://en.wikipedia.org/wiki/Four-ball_golf)
- **本件はユーザー要件が明示的に「2名側はスコアの平均」なので、平均を実装する。** ベターボール（良い方）は将来オプションの候補として §11 未決事項に上げるにとどめる（スコープ外）。
- **平均の性質（実装者向けの理解）**: ベターボールと違い、**下手な相方が平均を押し上げる**。「2名側＝2人の実力の中間」として扱われる。上手い1人を入れれば強くなる best-ball とは別物なので、幹事への説明文（`rule.match1v1`）に明記する。
- **運用上の値打ち**: 現行は人数差を「少ない側が2回出場」で吸収している（`2026-08-20-1on1-match.md` §4.2）。1対2があると **10人 vs 8人 → 8試合（1v1×6＋1v2×2）で全員ちょうど1回出場**が組める（10 = 6+2×2、8 = 6+2）。誰かが2回出る不公平を避けられる。

## 3. 計算仕様（★§3 追補・load-bearing）

### 3.1 何の平均か = ホールごと

各ホール `i` について、side の**メンバーの `adjHole` の平均**を出し、**平均どうしを比較**して 1UP / ハーフを決める。ラウンド合計の平均は使わない。

- 理由: `m1Result` は `for(i=0..17) m1HoleWin(...)` でホール勝敗を数える構造（`js/calc.js:124-127`）。ホール平均ならこの構造を1行も崩さずに一般化できる。合計平均だとマッチプレーではなくなる（UP 差が定義できない）。

### 3.2 基準スコア = `adjHole`（エブリ適用後）

コードで確認済み: `m1HoleWin` は `adjHole(g,pid,i)` を見ている（`js/calc.js:121`）。`adjHole` は `Number(v) - evPer(g,pid)`（`js/calc.js:30`）＝**エブリ適用後**。2名側の平均も**同じ `adjHole` の平均**とする（エブリ支給者が2名側にいれば、その支給ぶんが平均に反映される）。

### 3.3 端数：丸めない（既定案）

2名平均は必ず `x.0` か `x.5`。**丸めずにそのまま比較する。**

**丸めない根拠（数値で裏取り済み・§3.4／§3.5）**:
1. 四捨五入すると**勝者が変わる**。§3.4 の実例で「2名側 2UP」→「AS（引分）」に反転する。丸めは判定に効く二次ルールであり、説明コストに見合わない。
2. 「丸めないと引き分けが消える」は**成り立たなかった**。マッチ結果の引分（AS）率は乱数2000試合で **丸めなし 9.8% / 四捨五入 8.8%**（1v1 は 9.7%）＝ほぼ同じ。
3. ホール単位のハーフは減るが消えない: **1v1 平均 2.91H/18H → 1v2 丸めなし 1.45H/18H**（四捨五入なら 3.01H）。「平均が整数どうしで一致」したホールはちゃんとハーフになる。
4. 投影表示で `4.5` と出るほうが、なぜそのホールを取ったかが観客に一目で分かる。

**実装（浮動小数の等値判定を避ける）**: 平均そのものではなく**整数の交差乗算**で比較する。`adjHole` は必ず整数（スコア整数 − エブリ 0/1/2）なので、合計 `sum` と人数 `n` は整数。

```js
// 平均 sA/nA と sB/nB の大小を、割り算せずに整数比較する
const x = sA * nB, y = sB * nA;
return x < y ? 'A' : y < x ? 'B' : 'H';
```

- 1v1 では `nA=nB=1` → `x=sA, y=sB` ＝ **現行 `a<b?'A':b<a?'B':'H'` と完全に同一**（受け入れ条件 A1 の根拠）。
- 表示用の平均値だけ `Math.round(sum/n*10)/10` で丸める（**判定には使わない**）。

### 3.6 関数仕様（`js/calc.js`）

```js
// side = pid（文字列）| [pid,...]（配列）。以後 side を受ける関数はすべてこの共用体を取る
function m1Side(x){ return Array.isArray(x) ? x : [x]; }
// 表示・並び・m1Opened のキー（1名なら pid そのもの＝従来のキー文字列と一致）
function m1SideKey(x){ return m1Side(x).join('+'); }
// そのホールの side 合計と人数。1人でも未入力なら null（＝ホール無効・§3.7）
function m1SideSum(g, side, i){
  const a = m1Side(side); let s = 0;
  for(const pid of a){ const v = adjHole(g, pid, i); if(v == null) return null; s += v; }
  return { sum: s, n: a.length };
}
// 表示用の平均（判定には使わない）。1名なら整数のまま
function m1SideAvg(g, side, i){ const r = m1SideSum(g, side, i); return r ? Math.round(r.sum / r.n * 10) / 10 : null; }

function m1HoleWin(g, SA, SB, i){                    // ★シグネチャは同じ（第2/3引数が side になっただけ）
  const a = m1SideSum(g, SA, i), b = m1SideSum(g, SB, i);
  if(!a || !b) return null;
  const x = a.sum * b.n, y = b.sum * a.n;            // 平均比較の整数化（§3.3）
  return x < y ? 'A' : y < x ? 'B' : 'H';
}
function m1Result(g, SA, SB){ /* 中身は現行のまま。返り値 {upA,upB,half,played,diff} も不変 */ }
```

- `m1Result` の**返り値の形は変えない**（`results-m1.js` / `computePoints` / `teamWinPoints` の呼び出しはそのまま）。
- **1v1 の完全不変性**: `n=1` のとき `m1SideSum` は `{sum: adjHole, n:1}`、比較は `sum*1` どうし → 現行と同じ分岐に落ちる。`played===0`・`diff` の意味も不変。

### 3.7 欠測ホールの扱い（既定案 = 全員必須）

**2名側のどちらか1人でも未入力なら、そのホールは両側とも無効（スキップ）。**

- 根拠: 現行 `m1HoleWin` の「`a==null || b==null` → null」の最小の一般化。1v1 では挙動が1ビットも変わらない。
- 部分開封（`viewGameN`）は全選手のホールを同時にマスクするので、**開封演出には影響しない**（2名とも同じホールまで開く）。
- 実測例（選手B2 の H10 のみ未入力・他は §3.4 と同じ）:

| 案 | A勝ち | B勝ち | ハーフ | played | 結果 |
|---|---|---|---|---|---|
| **(b) 全員必須＝そのHスキップ（既定案）** | 8 | 9 | 0 | **17** | 2名側 1UP |
| (a) 入力のある人だけで平均 | 8 | 9 | 1 | 18 | 2名側 1UP |

（H10 は 単独側=6・B1=6・B2=未入力 → 案(a) の平均は 6 でハーフ、案(b) は無効。この例では最終結果は同じだが、**片方が途中リタイアした場合に案(a) は残り1名の生スコアが2名側の値になり、平均の意味が壊れる**ので (b) を推奨。）

## 4. 個人配点（`computePoints`）

### 4.1 既定案：2名側は山分け

```js
m1ValidPairs(g).forEach(([SA, SB]) => {
  const r = m1Result(g, SA, SB); if(!r.played) return;
  const give = (side, v) => { const a = m1Side(side); a.forEach(pid => { if(pts[pid] != null) pts[pid] += v / a.length; }); };
  if(r.diff > 0) give(SA, P.m1win);
  else if(r.diff < 0) give(SB, P.m1win);
  else { give(SA, P.m1draw); give(SB, P.m1draw); }
});
```

- **1v1 では `v/1 = v` ＝ 現行と完全に同じ**（`P.m1win`/`P.m1draw` の加算順序まで同じ）。

### 4.2 根拠：「1マッチ＝合計2pt」の不変量

既存の**既定値そのものが山分け思想を表している**: `m1win=2` / `m1draw=1` は、勝ち `2 = 0+2`、引分 `2 = 1+1` ＝ **どちらの結末でも1マッチが配る合計は 2pt** になるように選ばれている。山分けはこの不変量を1対2でも保つ。

また、チーム勝ち点は既に山分け実装（`teamWinPoints` の `wins[i] += w/winners.length`・`js/calc.js`）なので、「同じ賞に複数人がぶら下がるときは割る」という前例がある。

### 4.3 数値比較（§3.4 の3マッチ・`m1win=2 / m1draw=1`・賞金プール ¥15,000）

3マッチ = 「A2 vs B3（B3勝ち）」「A3 vs B4（A3勝ち）」「A vs B1+B2（2名側勝ち）」

| 案 | A | A2 | A3 | B1 | B2 | B3 | B4 | m1 合計pt |
|---|---|---|---|---|---|---|---|---|
| **山分け（既定案）** | 0 | 0 | 2 | **1** | **1** | 2 | 0 | **6** |
| 満額（各自に m1win） | 0 | 0 | 2 | **2** | **2** | 2 | 0 | **8** |

賞金配分（このm1配点だけがある場合の `computePayout`・プール¥15,000）:

| 案 | B1 | B2 | B3（1v1で勝った人） | A3（1v1で勝った人） |
|---|---|---|---|---|
| **山分け** | ¥2,500 | ¥2,500 | **¥5,000** | **¥5,000** |
| 満額 | ¥3,750 | ¥3,750 | **¥3,750** | **¥3,750** |

→ 満額案では「1対2で勝った人」が「1対1で勝った人」と同額になり、**1マッチだけ配分原資を2倍持っていく**（他の勝者が ¥5,000 → ¥3,750 に希釈される）。ここがユーザー確認事項（§11-2）。

引分の場合（山分け）: 単独側 `+1`・2名側 `+0.5` ずつ（合計2pt）。

### 4.4 小数ポイントの扱い

- 現状、**個人ポイントは常に整数**（配点はすべて整数の配列/定数）。山分けを入れると**初めて小数が出る**（`m1win=2` → `1`、`m1draw=1` → `0.5`）。
- 表示は `js/results.js:104` の `<b>${r.pt}</b>pt` ＝生の数値。`0.5` は `0.5pt` と表示される。
- **浮動小数の誤差は出ない**: 除数は常に side の人数（1 または 2）で、`整数/2` は2進浮動小数で厳密。3名 side を許すと `1/3` で誤差が出るため、**UI で side を2名までに制限する**（§6.1）ことが誤差回避としても効く。
- 気になる場合の代替: 表示側で `Math.round(pt*10)/10` を掛ける（配点の値自体は変えない）。**S レーンの磨きとして後追いで足せる**ので、本件では入れない。

## 5. `teamWinPoints`（種目別勝ち点）への影響 = なし

現行（`js/calc.js:252-256`）:

```js
m1ValidPairs(g).forEach(([a,b])=>{ const r=m1Result(g,a,b); if(!r.played)return; played++;
  if(r.diff>0)w[v.A.id]++; else if(r.diff<0)w[v.B.id]++; });
if(played) add('match1v1', teams.map(t=>w[t.id]!==undefined?w[t.id]:null),'desc');
```

- 種目値は「**チームが勝ったマッチの数**」。1対2の組も **1マッチ = 1勝** として数えるのが自然で、上のコードは `m1Result` が side を受けられるようになれば**そのまま正しく動く**（`a`/`b` を side として渡すだけ）。**変更不要。**
- 検算（§3.4 の3マッチ）: Red 1勝（A3）・Blue 2勝（B3、B1+B2） → `add('match1v1', [1,2],'desc')` → Blue が種目1位。マッチ数（3）は 1v1 のときと同じ数え方。
- **他8種目（teamGross / teamNet / holeByHole / best2ball / vegas / roulette / univMatch / niadora / customMatch）は 1 on 1 のデータを一切読まないので影響ゼロ。** 受け入れ条件で `tools/regress.mjs` の既存ケース差分ゼロを要求する（§9）。
- 補足: `anyTeamEvent`（ニアドラのチーム種目成立条件）に `F.match1v1` が入っているが、これはフォーマットのフラグを見るだけで pairs の形は見ない → 影響なし。

## 11. 未決事項（着手前にユーザー確認が要るもの）

1. **【要確認・最重要】端数の扱い**: 2名平均が `x.5` になったとき、**丸めずにそのまま比較**（既定案）でよいか。四捨五入すると §3.4 の実例で **「2名側 2UP」→「AS（引分）」** に結果が反転する。丸めなくてもマッチ引分率はほぼ変わらない（9.8% vs 8.8%）ことは実測済み。
2. **【要確認・最重要】個人配点**: 2名側が勝った/引き分けたとき、**2名で山分け**（既定案・勝ち1ptずつ／引分0.5ptずつ）か、**それぞれに満額**（2ptずつ／1ptずつ）か。満額だと、その1マッチだけ賞金原資の取り分が2倍になり、1対1で勝った人の配分が ¥5,000 → ¥3,750 に希釈される（§4.3）。**山分けだと個人ポイントに初めて `0.5` が出る**点も併せて確認したい。
3. **2名側の最大人数**: 2名までで確定してよいか（1対3以上は作らせない）。計算は N 名で一般に動くが、UI で2名に制限すると小数ポイントが `0.5` 刻みに収まり、平均も `x.0/x.5` に収まる（表示が読みやすい）。
4. **2対2 を許すか**: 提案の4セレクトUIだと **2対2 も自然に作れてしまう**（左右とも2人目を選べるため）。禁止したいなら「片方は必ず1名」のバリデーションを1本足す（実装コストは小）。既定案は**許す**（ベスト2ボールとは別物なので混乱は小さいと判断）。
5. **欠測ホール**: 2名側の1人が未入力のホールを**そのホールごと無効**（既定案）でよいか。「入力のある人だけで平均」にすると、片方が途中リタイアしても最後までマッチが続く（ただし平均の意味が途中で変わる）。
6. **ベターボール（良い方）オプション**: ゴルフの一般慣例は 1 vs 2 は**ベストボール（2名の良い方）**（§1）。将来「平均／良い方」をマッチごとに選べるようにする需要があるか。あるならデータに `mode` を持たせる場所（`pairs` 要素を `{a,b,mode}` に拡張）を今のうちに決めておきたい。**今回はスコープ外。**
7. **未出場チェックの扱い**: 1対2を使うと「全員1回以上出場」が組みやすくなる（§1）。`m1.notPlayed` の警告文はそのままでよいか（変更不要と判断しているが、運用文言の好みがあれば）。
8. **テストデータ p7 の要否**（PR-C）。
