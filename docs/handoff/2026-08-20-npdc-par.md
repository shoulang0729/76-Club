# ニアピン/ドラコン対象ホールのパー連動（Par 3=NP / Par 5=DC）設計

- 日付: 2026-08-20（起案）/ 2026-08-29（設計確定）
- 対象: コースタブ NPDC カード・賞タブ（勝者登録）・配点（computePoints）・テストデータ
- 正本との関係: **§3.6（計算・個人賞）と §4（データモデル prizes）に触れる** → 正本 `2026-07-12-golf-compe-web.md` §3.6・§4 に同日付の最小追補を実施（本ファイルが詳細の正）。
- 基準コミット: main = 44ba6a6

## 1. ユーザー確定要件

1. ニアピン/ドラコン対象ホールは**パー設定から自動で決まる**: **Par 3=ニアピン、Par 5=ドラコン**（コンペの固定ルール）。
2. 手動での対象ホール指定 UI（holebtn の `cyclePrize` トグル）は**廃止**。パー変更に対象ホールが追従。
3. コースタブに自動判定結果の表示を残す（例: 「ニアピン: 3H・8H・12H・17H ／ ドラコン: 5H・14H」）。Par3/Par5 が何個あっても**すべて対象**（個数制限なし）。

## 2. 決定事項サマリ（決め切り）

| 論点 | 決定 |
|---|---|
| 導出方式 | **A: 純関数導出**。`niapinHolesOf(g)` / `draconHolesOf(g)`（js/state.js に追加）を全参照箇所が呼ぶ。`g.prizes.niapinHoles/draconHoles` への**書き込み同期はしない** |
| 既存フィールド | `g.prizes.niapinHoles` / `draconHoles` は**残置・非参照（deprecated）**。newGame/migrate のスキーマは不変（削除・改名なし） |
| 勝者データ | `niapinWinner` / `draconWinner`（キー=ホールindex）は**そのまま**。導出対象外ホールのエントリは**削除せず保持し、表示・集計から無視**（非破壊・可逆） |
| 旧手動値との食い違い | **黙って自動優先**（通知・confirm なし）。勝者登録済みホールが対象外になった場合も同じ（§5 ケース表） |
| パー未設定(0/空) | `par===3` / `par===5` の**厳密一致**のみ対象 → 0 や空は対象外 |
| §4 の意味づけ | 変わる（holes 配列が「設定値」→「廃止フィールド」）→ **正本 §4 に追補する** |
| 配点走査 | calc.js を「winner 全走査」→「**導出対象ホールのみ走査**」に変更（§3 前後比較を §4 に記載・load-bearing） |

### 2.1 なぜ B案（パー変更時に g.prizes.*Holes を自動同期）にしないか
- 同期ポイントが増える（setPar / migrate / backup import / testdata / 将来のパー編集経路）と**取りこぼし＝陳腐化データ**のリスクが残る。純関数なら single source of truth = `g.par` で常に整合。
- B案でも calc は winner 全走査のままでは「対象外ホールの勝者に加点」が残る（同期時に winner を消すと**破壊的**で不可逆）。A案は winner を保持したまま集計だけ絞れるため、パーを戻せば勝者登録も復活する（可逆）。

## 3. 導出関数（js/state.js に追加・グローバル関数）

```js
/* NPDC 対象ホールはパーから導出（Par3=ニアピン / Par5=ドラコン・2026-08-20-npdc-par.md）。
   g.prizes.niapinHoles/draconHoles は廃止フィールド（後方互換のため残置・非参照） */
function niapinHolesOf(g){ return g.par.map((p,i)=>p===3?i:-1).filter(i=>i>=0); }
function draconHolesOf(g){ return g.par.map((p,i)=>p===5?i:-1).filter(i=>i>=0); }
```

- 戻り値はホール index（0始まり）の**昇順配列**（map/filter の性質で保証）→ 既存の `.slice().sort()` は不要。
- 関数名はプロパティ名 `niapinHoles` との混同を避けて `〜Of(g)` とする。
- 置き場所は js/state.js（読込順の先頭・データモデル系ヘルパー。全モジュールから onclick 経由でなく描画時に呼ばれるため読込順の制約はないが、データ導出は state.js に集約する）。

## 4. 配点の変更（js/calc.js:149-150）— ★§3 load-bearing・前後比較

**前（現行）**: winner オブジェクトの**全エントリ**に加点（登録さえあればホールが対象かどうかを見ない）。

```js
Object.values(g.prizes.niapinWinner||{}).forEach(pid=>{ if(pid&&pts[pid]!=null)pts[pid]+=(P.niapin||0); });
Object.values(g.prizes.draconWinner||{}).forEach(pid=>{ if(pid&&pts[pid]!=null)pts[pid]+=(P.dracon||0); });
```

**後**: **導出対象ホールのみ**走査して加点。

```js
niapinHolesOf(g).forEach(h=>{ const pid=(g.prizes.niapinWinner||{})[h]; if(pid&&pts[pid]!=null)pts[pid]+=(P.niapin||0); });
draconHolesOf(g).forEach(h=>{ const pid=(g.prizes.draconWinner||{})[h]; if(pid&&pts[pid]!=null)pts[pid]+=(P.dracon||0); });
```

**数値例（前後比較）**: `P.dracon=2`。5H（index 4）が Par5 でドラコン勝者=山田を登録済み → その後 5H のパーを 4 に変更。
- 前: `draconWinner["4"]="山田"` が残るため山田に **+2pt のまま**（手動 holes 配列もパー変更に無関係なので登録UIにも残る）。
- 後: 5H は導出対象外 → 山田 **+0pt**（賞タブの登録UIにも出ない）。エントリ自体は保持されるので、パーを 5 に戻すと登録・+2pt が**そのまま復活**。
- 対象ホールで勝者登録されている通常ケースは**前後で同点**（1件につき `P.niapin`/`P.dracon` 加点＝不変）。

winner のキーはこれまで通り**ホール index の文字列**（JSON化でキーは文字列になるが、JS のプロパティアクセス `obj[4]` と `obj["4"]` は同一なので互換）。
