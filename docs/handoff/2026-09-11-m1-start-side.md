## 1. 要件と現状

### 1.1 ユーザー要件（原文）

> （バックログ）1on1でOutスタートとInスタートとでそれぞれ開けていく9ホールの順序も調整可能にしたい

### 1.2 現状（コードで確認・2026-09-11 時点の main / PR #137 まで）

1 on 1 の開封は2モード（`js/results-m1.js`）:

| モード | 状態 | マスク |
|---|---|---|
| `m1RevealMode='all'`（全組一括・既定） | 結果発表タブ共通の `revealHoles`（揮発） | `gAll = viewGame(g)` を**全カード共通**で使用（`js/results-m1.js:39`） |
| `m1RevealMode='one'`（一組ずつ） | 組ごとの開封数 `m1Opened`（Map・揮発・キー=`pidA:pidB`） | カードごとに `viewGameN(g, c)`（`js/results-m1.js:83`） |

マスクの実体は `js/results.js:48`:

```js
function viewGameN(g,n){
  if(n>=18) return g;
  const scores={};
  g.participants.forEach(pid=>{ const a=g.scores[pid]||[]; scores[pid]=a.map((v,i)=> i<n? v : null); });
  return Object.assign({}, g, {scores});
}
```

`i < n` ＝ **常に 1H → 18H のホール番号順**。したがって **10番スタートの組は、実際には最後に回った 1〜9H が先に開く**。
これが今回の要件の動機（2ウェーブ運用で、IN スタート組の「めくり」が実況と逆行する）。

### 1.3 スコープ外（本設計では扱わない）

- ルーレット・チーム戦・大学対抗・スコアカードなど **1 on 1 以外の画面の開封順**（`revealHoles` の意味は不変）
- 配分タブ（`renderStanding`）の暫定表示 … §5.2 の既知の限界として明記するのみ
- 「組（パーティ）」概念の導入（候補 J・#132 §3.1 案2）… §7.2

## 2. データモデル（正本 §4 追補案）

### 2.1 粒度の決定：**組（ペア）ごと**

| 案 | 表現できること | 判定 |
|---|---|---|
| コンペ全体で1値（`g.m1Start`） | 「今日は全員 IN スタート」だけ | **却下**。2ウェーブ（OUT組と IN組が混在）を表現できない＝今回の動機そのものを解けない |
| マッチ全体で1値（`g.match1v1.start`） | 同上（1 on 1 タブ内で一律） | **却下**。同じ理由 |
| **組（ペア）ごと** | OUT組・IN組の混在／ショットガン時の任意スタート | **採用** |

**なぜペア単位で足りるのか**: マッチプレーは「同じ組で回った2人（#124 後は2〜3人）の直接対決」。異なる組に分かれた2人を対戦させる運用は存在しない（比較の前提が崩れる）。
よって **1ペア = 1組 = 1スタートホール** が成立する。ペアより細かい粒度（選手ごと）は不要。

### 2.2 保持形式の決定：キー付きオブジェクト

```jsonc
// g.match1v1（既存）に 1 フィールド追加するだけ
"match1v1": {
  "teamA": "<teamId>",           // 変更なし
  "teamB": "<teamId>",           // 変更なし
  "pairs": [ ["pA1","pB1"], … ], // 変更なし（#124 で共用体化されても本設計は無影響・§7.1）
  "starts": {                    // ★追加。既定（OUT=1H）の組は**キーを持たない**
    "pA2:pB2": 10                // キー = m1Key(a,b)（= m1Opened と同じキー）／値 = 1-based スタートホール
  }
}
```

| 論点 | 決定 | 根拠 |
|---|---|---|
| 配列（`pairs[i][2]`）に足すか | **足さない** | #124 が `pairs` の要素を「`side | side[]` の2要素」に共用体化する。そこへ**意味の違う第3要素**を混ぜると `pair.map(m1Side)` 系の一般化コードが踏む（§7.1） |
| 並列配列（`starts:[…]`・index 対応）か | **しない** | `m1MovePair`／`m1DelPair` のたびに index を同期する保守が発生し、ズレると**別の組のスタート側になる**（サイレントな誤り） |
| キー付きオブジェクト | **採用** | `m1Opened`（Map）と**同じキー体系**＝並べ替え・削除に不変。既に実績のある識別子を再利用する |
| 既定値の持ち方 | **キーなし = OUT（1H）** | 既存データ・既存バックアップが**そのまま既定 OUT** で読める。`migrate` は1行のガードだけ（§2.4） |
| 値の型 | **数値の 1-based スタートホール**（`1`〜`18`） | 'out'/'in' の2値にすると #132／候補 J と統合するとき**必ず変換が要る**。数値なら解決関数の戻り値の型が最初から一致（§7.2）。写像式もそのまま使える |
| localStorage キー | **増やさない**（`golfCompe_v1` 内） | CLAUDE.md load-bearing |
| 削除時の掃除 | `m1DelPair` / `m1ClearAll` で該当キーを `delete` | 孤児キーが残ると、同じ組を作り直したときに**前回のスタート側が復活**して驚く |

### 2.3 データ（永続）にする根拠

- スタート側は **当日の運営事実**（組分け表に書いてある）であり、表彰式で再読込しても失われてはならない。
- 表彰式は「幹事のスマホで入力 → 会場の画面で開封」という時間差がある。揮発にすると**会場で入れ直し**になる。
- 一方 **開封の進み具合**（`m1Opened` / `revealHoles`）は演出の進行状態なので、正本 §11.14 の原則どおり**揮発のまま**（保存しない）。
  → 「事実＝データ／演出の進行＝揮発」の線引きは既存のまま一貫する。

### 2.4 migrate / 既存データ

```js
// js/state.js migrate() 内（既存の match1v1 行の直後）
if(!g.match1v1.starts || typeof g.match1v1.starts!=='object') g.match1v1.starts={};
```

- `newGame()` の `match1v1:{teamA:null,teamB:null,pairs:[],starts:{}}` に1語追加。
- 既存ゲーム・旧バックアップは `starts={}` ＝**全組 OUT** ＝現行と完全に同じ挙動。
- 旧版 JS がキャッシュされたブラウザで新形式を開いた場合: `starts` を誰も読まない＝**全組 OUT で表示される**だけ（例外なし・データも壊れない）。
- `dupGame()`（`js/basic.js`）は `JSON.parse(JSON.stringify())` の深いコピー＝**無改修で追随**。`js/backup.js` も state 丸ごと出力なので**変更不要**。

## 3. マスクの実装方針

### 3.1 順序写像（式・node 実測済み）

巡回長 `HN = 18`（アプリの 18 ホール前提。`g.par.length` を使ってもよいが本設計では 18 固定で書く）。
スタートホール `s`（1-based）の組について:

```
holeAt(k, s) = ((s - 1) + k) mod 18        // 開封順 k 番目(0-based) に開く「実ホール index(0-based)」
off(i, s)    = (i - (s - 1) + 18) mod 18   // 実ホール index i が「その組の何ホール目か」(0-based)
```

- 両者は互いに逆写像（`off(holeAt(k,s),s) === k` を `s ∈ {1,4,10,16}` の全 k で実測・一致）。
- `s=1`（OUT）… `holeAt` は恒等写像 `k → k`。**既存 `viewGameN` と完全に一致**（§6.3 で実測）。
- `s=10`（IN）… 開封順は **10,11,…,18,1,2,…,9**（＝要件の「9ホールで折り返す」）。

**「9ホール折返し」で正しいか**: 正しい。ただし**折返しを特別扱いしない**のが本設計の要点で、`s=10` は上式の一事例にすぎない。
ショットガン（例 `s=7`）を入れても式は不変（`7,8,…,18,1,…,6`）＝**任意スタートホールに最初から一般化されている**。
UI だけを OUT/IN の2択に絞る（§4.3・§13 の未決①で任意ホール入力の要否を確認）。

### 3.2 派生関数（`js/results.js` の `viewGameN` は触らない）

`viewGameN` の呼び出し元は **`js/results.js:55`（`viewGame`）・`js/results-m1.js:49` ・`js/results-m1.js:83`** の3箇所だが、
`viewGame(g)` 経由で **スコア表・個人戦・チーム戦（グロス/ネット/HBH/ベスト2/ベガス）・大学対抗・配分タブ**が全部ぶら下がっている。
→ **`viewGameN` には一切触らない。1 on 1 専用の派生関数を `js/results-m1.js` に新設する**（新規ファイルは作らない）。

```js
/* 1 on 1 専用: スタートホール s（1-based）の組が「n ホール目まで回った」状態のビューゲーム。
   s=1（OUT・既定）では viewGameN にそのまま委譲＝既存挙動とバイト一致。 */
function m1Off(i,s){ return (i-(s-1)+18)%18; }
function m1ViewGameN(g,n,s){
  if(!(s>1)) return viewGameN(g,n);          // OUT / 未設定 / 不正値 → 従来どおり
  if(n>=18) return g;
  const scores={};
  g.participants.forEach(pid=>{ const a=g.scores[pid]||[]; scores[pid]=a.map((v,i)=> m1Off(i,s)<n ? v : null); });
  return Object.assign({}, g, {scores});
}
/* ペアのスタートホール解決（★将来 #132／候補J と統合するときに差し替える唯一の場所） */
function m1StartOf(g,k){ const s=((g.match1v1||{}).starts||{})[k]; return (s>=1&&s<=18)?s:1; }
```

- `g.participants` を回す点・`Object.assign` で浅くコピーする点は `viewGameN` と**同型**（挙動の差は `i<n` → `m1Off(i,s)<n` だけ）。
- **`m1StartOf` に参照を閉じる**のは #132 の `sgGroups(g)` と同じ手口（§7.2）。

### 3.3 呼び出し側の差し替え（`js/results-m1.js`）

| 現行 | 変更後 |
|---|---|
| `const gAll=viewGame(g);`（39行） | 残す。**全組 OUT のときの高速パス**として使う |
| サマリ（49行）`m1Result(viewGameN(g, c), a, b)` | `m1Result(m1ViewGameN(g, c, m1StartOf(g,k)), a, b)` |
| サマリ（50行）`m1Result(gAll, a, b)` | `const s=m1StartOf(g,k); m1Result(s===1?gAll:m1ViewGameN(g,n,s), a, b)` |
| カード（83行）`const gc = one? viewGameN(g,c) : gAll;` | `const s=m1StartOf(g,k); const gc = one ? m1ViewGameN(g,c,s) : (s===1?gAll:m1ViewGameN(g,n,s));` |

→ **全組 OUT（既定・既存データ全部）なら `gAll` / `viewGameN` がそのまま使われ、生成される HTML は現行と1文字も変わらない**（受け入れ条件 A1）。

## 5. 計算・結果への影響（§3 非接触の論証）

### 5.1 最終結果（勝敗・UP数）は開封順に依存しない — 論証と実測

`js/calc.js:124`:

```js
function m1Result(g,pidA,pidB){ let upA=0,upB=0,half=0;
  for(let i=0;i<18;i++){ const w=m1HoleWin(g,pidA,pidB,i);
    if(w==='A')upA++; else if(w==='B')upB++; else if(w==='H')half++; }
  return { upA, upB, half, played:upA+upB+half, diff:upA-upB }; }
```

1. `m1HoleWin(g,A,B,i)` は **ホール `i` 単体の関数**（他ホールを参照しない・`js/calc.js:121`）。
2. `m1Result` は 18 ホールぶんの結果を**加算（可換・結合的）**しているだけ。**タイブレークも打ち切りも無い**（「3&2 で終了」のような早期確定を実装していない）。
3. よって `m1Result` は「勝敗の**多重集合**」の関数であり、**並び順に不変**。
4. `n=18` では `m1ViewGameN` は `g` をそのまま返す（`s` に関わらず同じオブジェクト）＝**入力すら同一**。

→ **実測**（§6.3）: 同一スコアで `s=1 / 10 / 7` の全開封結果は `{upA:8,upB:7,half:3,played:18,diff:1}` で**完全一致**。

### 5.2 変わるのは「暫定表示（途中経過）」だけ、で正しいか

| 対象 | 影響 |
|---|---|
| 1 on 1 カードの hero（`◀ nUP` / `AS`）・ホール表・暫定タグ | **変わる**（＝これが要件。途中経過が実際の巡回順に沿う） |

| 配分タブ（`renderStanding`） | **変わらない**（`viewGame(g0)`＝共通 `revealHoles` の 1H→18H マスクのまま）。**既知の限界**: 部分開封中は 1 on 1 タブの暫定表示と配分タブの m1 加点が別基準になる。全開封（18/18）では一致する。今回は**触らない**（§11 触らない範囲）→ §13 未決② |
