## 1. 要件（ユーザー原文）

> コースデータをよく行くコースについて保存したい
> コースデータのショート・ロングについては、自動的にニアドラをデフォルト設定

**設計の一言まとめ**: よく行くコースの **名前＋18ホールのパー** を `state.courses` に保存し、コンペのコース設定へ**コピー方式**で読み込めるようにする。読み込んだ瞬間 `g.par` が埋まるので、ニアピン(Par3)/ドラコン(Par5) は**現行の導出ロジックのまま自動で決まる**（要件2は追加実装ゼロ・§3 参照）。

- localStorage キーは**増やさない**（`golfCompe_v1` の中で完結）。
- 新規 JS ファイルを作らない（`index.html` の読込順は変更しない）。

## 3. 【要件2】ショート/ロングのニアドラ自動設定 — **現行で充足済み・追加実装なし**

### 3.1 根拠（現行コード）

`js/state.js:70-73`:

```js
/* NPDC 対象ホールはパーから導出（Par3=ニアピン / Par5=ドラコン・2026-08-20-npdc-par.md）。
   g.prizes.niapinHoles/draconHoles は廃止フィールド（後方互換のため残置・非参照） */
function niapinHolesOf(g){ return g.par.map((p,i)=>p===3?i:-1).filter(i=>i>=0); }
function draconHolesOf(g){ return g.par.map((p,i)=>p===5?i:-1).filter(i=>i>=0); }
```

- 日本語ゴルフ慣用の **ショートホール＝Par 3 / ミドル＝Par 4 / ロング＝Par 5** は、この導出とそのまま一致する。
- 手動での対象ホール指定 UI は 2026-08-20 に**廃止済み**（`2026-08-20-npdc-par.md` §1-2）。対象ホールは `g.par` の**単一ソース**から常に導出され、個数制限はない。
- 追従も既に実装済み: `js/course.js:27` の `setPar()` が `renderCourse()` を呼び、NPDC カード（`js/course.js:15-23`）が即時再描画される。賞（勝者登録）と配点（`calc.js` の NP/DC 加点）も同じ導出関数を参照する。

### 3.2 結論

| 問い | 結論 |
|---|---|
| 要件2のために新しいコードが要るか | **要らない**。`g.par` に値が入りさえすれば NP/DC は自動で決まる |
| ではユーザーの要望は何で満たされるか | **要件1（コースマスタ）の帰結**。「よく行くコース」をマスタから読み込む＝`g.par` が18ホール分まとめて入る＝ショート/ロングのニアドラが**その場で全部決まる**。現在は毎回18個のパーを手入力しているため「自動になっていない」と感じられている、という読み |
| マスタに「ショート/ロングの明示フラグ」を持たせるか | **持たせない**。`par===3` / `par===5` から導出できる**冗長データ**であり、二重管理は `2026-08-20-npdc-par.md` §2.1 が退けた B 案（同期ポイントを増やす）そのもの。単一ソース = `courses[].par` を守る |

→ 本設計の受け入れ条件 §8 に「読込直後、追加操作なしで NPDC カードに Par3/Par5 のホールが並ぶ」を入れて**回帰で守る**。

### 3.3 積み残し（本設計のスコープ外・§12 Q2）

実在コースは Par3×4・Par5×4（par 72）が典型で、**NP が4ホール・DC が4ホールになる**。運用では DC を 1〜2 ホールに絞ることも多いが、現行は個数制限なし（`npdc-par.md` §1-3 でユーザー確定済み）。マスタ導入で「本物のコース構成」を読み込む機会が増えるため顕在化しうる。対象ホールを個別に OFF する機能は **§3.6 の改訂を伴う load-bearing 変更**なので、本設計では扱わず §12 Q2 に上げる。

## 4. データモデル

### 4.1 追加スキーマ（正本 §4 追補）

```jsonc
{
  "players": [...],
  "games":   [...],
  "currentGameId": "g1",
  "courses": [ {                      // ★新設（既定 []）。localStorage キーは増やさない（golfCompe_v1 の中）
      "id": "c1",                     // uid()
      "name": "○○CC",                 // 表示名。空可（空なら i18n clib.untitled で表示）
      "par": [4,4,3,4,5,4,4,3,4, 4,4,3,4,5,4,4,3,4],   // length 18・唯一の実体データ
      "note": "",                     // 任意メモ（例「バックティー」「東→西」）
      "updatedAt": "2026-09-06"       // 保存/上書き日（一覧の既定ソートキー）
  } ]
}
```

ゲーム側に**弱参照**を1つ追加する:

```jsonc
"games": [ { ..., "course": "○○CC", "courseId": "c1" } ]   // courseId は null 可・計算からは一切参照されない
```

### 4.2 項目の採否（過不足の検討）

| 項目 | 採否 | 理由 |
|---|---|---|
| `name` | **採用** | 選択 UI の見出し。読込時に `g.course`（既存の文字列）へコピー＝ヘッダ表示がそのまま生きる |
| `par[18]` | **採用** | 本体。これ1つで NP/DC・規定打数・隠し12抽選の帯分類まで決まる |
| `note` | **採用** | 「バックティー」「東→西」など**同名コースの区別**に要る。フリーテキスト1つで十分（ティー区分の構造化は §12 Q1 の回答待ち） |
| `updatedAt` | **採用** | 一覧の既定ソート（新しい順）＋「いつ保存したか」の目安。`new Date().toISOString().slice(0,10)`（`newGame()` の date と同じ作り） |
| `id` | **採用** | `uid()`。改名しても参照が壊れない（`team.id` の前例・`custom-match.md` §4.1） |
| `hidden[18]` | **不採用** | 隠し12は**そのコンペの抽選結果**であってコースの属性ではない。同じコースで毎回引き直すのが仕様（`hidden12-balance.md`）。マスタに入れると「前回の抽選が復活する」不正な挙動になる |
| ショート/ロング フラグ | **不採用** | §3.2。`par` から導出できる冗長データ |
| ホール名（`W1..N9` 等）／OUT・IN の呼称 | **Phase A では不採用**（Phase C で検討） | 表示するには score/course/results/roulette の**全ホール表のヘッダ**に手を入れる必要があり、Phase A の 10 倍の影響範囲になる。データだけ先に持たせても**消費者ゼロの死にフィールド**になるため持たない。追加が必要になったら migrate の per-key バックフィル（`state.js:24-28` の前例）で後付けできる＝**今決めなくてよい** |
| ヤード数・コースレート・HDCP インデックス | **不採用** | §3 のどの式も参照しない（`parTotal` すら par 合計のみ）。消費者のないデータを持たない |
| ペリア係数・上限などの集計ルール | **不採用** | コースではなく**コンペの設定**（`g.periaCoef` 等）。混ぜない |
| `courseId`（ゲーム側） | **採用** | 「上書き保存」の宛先と「どのコースから読んだか」の表示のためだけの**弱参照**。計算は一切参照しない。マスタ削除で dangling になっても `find` が `undefined` を返す＝未リンク扱いで無害（`custom-match.md` §4.1 の孤児エントリ放置と同じ方針） |

### 4.3 migrate / 既存データ

`js/state.js` の `migrate(s)` 冒頭に2行だけ足す:

```js
if(!Array.isArray(s.courses)) s.courses=[];          // コースライブラリ（2026-09-06-course-master.md §4）
(s.games||[]).forEach(g=>{ if(g.courseId===undefined) g.courseId=null; });   // 既存 forEach 内に1行でも可
```

- `newGame()` に `courseId:null` を追加（`course:""` の直後）。
- **既存ゲームからのマスタ自動生成はしない**（決定）。理由:
  1. `g.course` は自由入力の文字列で、空・表記ゆれ・テストデータ（`テスト国際CC`）が混在する → **ノイズだらけのマスタ**になる。
  2. migrate が**データを増やす**のは非可逆で、バックアップ再取込のたびに重複が増える危険がある（migrate は冪等であるべき）。
  3. 代替が1タップで済む（§6.2 の「現在の設定を保存」）。ユーザーは実際に使うコースだけを能動的に登録できる。
- 旧バックアップ（`courses` なし）の取込は `importData` → `migrate(s)` で `courses:[]` が補完される＝**backup.js は無改修**。`exportData` は `state` 全体を JSON 化するので `courses` は自動的に含まれる（`js/backup.js:2`）。受け入れ条件 §8 で往復を確認する。

### 6.2 保存

| ボタン | 条件 | 挙動 |
|---|---|---|
| **現在の設定を保存**（新規） | 常時（ゲーム選択中） | `state.courses.push({id:uid(), name: g.course.trim() \|\| t('clib.untitled'), par: g.par.slice(), note:'', updatedAt: today})` → `g.courseId=新id` → `save()` → `renderCourse()` → `toast(clib.savedT)` |
| **上書き保存** | `g.courseId` が `state.courses` に**実在するときだけ**表示 | `confirm(clib.cfmUpdate)` → `c.par=g.par.slice(); c.updatedAt=today;`（**name/note は上書きしない**＝ユーザーが管理表で付けた名前を壊さない） → `save()` → `toast(clib.updatedT)` |

- `prompt()` は使わない。名前は基本設定の「コース」欄（`g.course`）から取り、以後は管理表でインライン編集する（`players.js` の登録済み表と同じ作法）。
- `par` は必ず `slice()` で**値コピー**（参照共有は「マスタが勝手に書き換わる」バグの温床）。

### 6.3 読込

```
loadCourse(id):
  c = state.courses.find(x=>x.id===id); if(!c) return;
  if(!confirm(t('clib.cfmLoad',{name:c.name}))) return;
  g.par = c.par.slice();        // ★書き込むのはここだけ
  g.course = c.name;            // ヘッダ・基本設定の表示名も揃える
  g.courseId = c.id;
  save(); render();             // renderCourse ではなく render()（ヘッダと基本設定タブの表示名も更新するため）
  toast(t('clib.loadedT'));
```

- **`g.hidden` は触らない**（§5）。パーが変わって隠し12の帯配分が崩れる可能性があるので、確認ダイアログと読込後の muted 注記で「隠し12は変わりません。必要なら『隠し12ランダム』で引き直してください」と誘導する（ボタンは同じ画面のすぐ下にある）。自動で引き直すと**ペリア HDCP が黙って変わる**＝ §3 への隠れた介入になるので採らない。
- **スコア入力済みでも読込を禁止しない**（禁止すると当日「パーを1つ間違えた」の訂正すらできなくなる）。`confirm` 1枚で足りる。
- 読込直後、NPDC カードは `renderCourse()` の再描画で**自動的に新しい Par3/Par5 を表示する**（要件2の充足点）。

### 6.4 編集・削除（管理 `<details>` 内）

| 操作 | 挙動 |
|---|---|
| 名前の変更 | `<input onchange="setCourseField('<id>','name',this.value)">` → `updatedAt` は**更新しない**（パーの版とは別物なので）。既に読み込み済みのコンペの `g.course` は**追随しない**（コピー方式・§6.5） |
| メモの変更 | 同上（`note`） |
| パーの編集 | **Phase A では提供しない**。「コンペに読み込む → 既存のパー表で直す → 上書き保存」で完結する。パー編集グリッドを2箇所に持つと `courseGrid` の重複実装になるため（§12 Q4） |
| 削除 | `confirm(t('clib.cfmDelete',{name}))` → `state.courses = state.courses.filter(...)`。**ゲーム側は何も壊れない**（`g.par` は値コピー済み）。他ゲームの `g.courseId` は dangling のまま残置＝「上書き保存」ボタンが消えて未リンク扱いになるだけ（§4.2） |
| 読み込む（行内） | §6.3 と同じ |

### 6.5 コピー方式（決定）

**読み込んだ後にコンペ側でパーを編集しても、マスタは変わらない。** 逆にマスタを編集してもコンペは変わらない。反映は**明示的な「上書き保存」だけ**。

- 理由: ラウンド当日に「17番のパーが違った」と直すのは**そのコンペの訂正**であって、ライブラリの改訂とは限らない。参照方式（`g.courseId` を計算が引く）にすると、マスタを1つ直しただけで**過去の全コンペの HDCP と順位が変わる**（＝ §3 の結果が遡って変わる）。これは絶対に避ける。
- 副次効果: 既存の全計算コードが `g.par` を読むだけで済む＝ `calc.js` 無改修（§5）。

### 6.6 その他の連動

- `dupGame()`（`basic.js`）は JSON 深コピー → `courseId` も複製される。複製先も同じマスタにリンクしたまま＝仕様として正しい。**改修不要**。
- `deleteGame()` はゲームを消すだけ。マスタは残る。**改修不要**。
- 一覧の並び: `updatedAt` 降順（新しい順）。同日はの追加順（`courses` の配列順）。**ソート UI は作らない**。

## 8. 受け入れ条件

**A. 保存・読込（要件1）**
1. コースタブ先頭に「コースライブラリ」カードが出る。ライブラリが空のときは `clib.empty` が管理表の位置に出る。
2. パーを入力した状態で「現在の設定を保存」→ セレクトにその名前が出る（名前は基本設定の「コース」欄の値。空なら「名称未設定コース」）。
3. 別のコンペを新規作成 → セレクトで選んで「読み込む」→ confirm を OK → **18ホールのパーがマスタの値と一致**し、ヘッダと基本設定の「コース」欄にマスタ名が入る。
4. 読込後にコンペのパーを1つ変えても**マスタの値は変わらない**（管理表の「パー合計」が変わらない）。
5. 「上書き保存」は**リンク中のみ**表示され、押すとマスタの par と更新日だけが変わる（名前・メモは保持）。
6. 管理表で名前／メモをインライン編集でき、削除すると一覧から消える。**削除しても、そのコースを読み込んだ既存コンペのパー・スコア・順位は一切変わらない**。

**B. ニアドラ自動（要件2）**
7. Par3×4・Par5×4 のコースをマスタから読み込むと、**追加操作なしで**同じ画面の「ニアピン / ドラコン ホール」カードに 4ホールずつ並ぶ。
8. 結果タブの NP/DC 勝者登録の対象ホールも同じ 4＋4 になる（`prize.emptyCfg` が出ない）。

**C. データ・非回帰**
9. `g.hidden` は読込・保存のどの操作でも変化しない（読込前後で隠しホールのチェック位置が同一）。
10. JSON 書き出し → 別ブラウザ／シークレットで読み込み → **ライブラリが復元される**。`courses` を持たない**旧バックアップ**も従来どおり読め、ライブラリは空で開始する。
11. `node tools/verify.mjs` 全 PASS（i18n 3言語パリティ／未定義参照ゼロ／未使用キーゼロ／孤立 var() ゼロ／計算回帰）。
12. `node tools/regress.mjs` が **`--update` なしで PASS**（＝計算スナップショット差分ゼロ）。`js/calc.js` の差分が**0行**であること。
13. `index.html` の `?v=` を PR 番号に一括更新。
