## 3. 【要件2】ショート/ロングのニアドラ自動設定 — **現行で充足済み・追加実装なし**

### 3.1 根拠（現行コード）

`js/state.js:70-73`:

```js
/* NPDC 対象ホールはパーから導出（Par3=ニアピン / Par5=ドラコン・2026-08-20-npdc-par.md）。
   g.prizes.niapinHoles/draconHoles は廃止フィールド（後方互換のため残置・非参照） */
function niapinHolesOf(g){ return g.par.map((p,i)=>p===3?i:-1).filter(i=>i>=0); }
function draconHolesOf(g){ return g.par.map((p,i)=>p===5?i:-1).filter(i=>i>=0); }
```

- 日本語ゴルフ慣用の **ショートホール＝Par 3 / ミドル＝Par 4 / ロング＝Par 5** は、この導出とそのまま一致する。
- 手動での対象ホール指定 UI は 2026-08-20 に**廃止済み**（`2026-08-20-npdc-par.md` §1-2）。対象ホールは `g.par` の**単一ソース**から常に導出され、個数制限はない。
- 追従も既に実装済み: `js/course.js:27` の `setPar()` が `renderCourse()` を呼び、NPDC カード（`js/course.js:15-23`）が即時再描画される。賞（勝者登録）と配点（`calc.js` の NP/DC 加点）も同じ導出関数を参照する。

### 3.2 結論

| 問い | 結論 |
|---|---|
| 要件2のために新しいコードが要るか | **要らない**。`g.par` に値が入りさえすれば NP/DC は自動で決まる |
| ではユーザーの要望は何で満たされるか | **要件1（コースマスタ）の帰結**。ライブラリから「西→北」を選ぶ＝`g.par` が18ホールぶん埋まる＝ショート/ロングのニアドラが**その場で全部決まる**。現在は毎回18個のパーを手入力しているため「自動になっていない」と感じられている、という読み |
| マスタに「ショート/ロングの明示フラグ」を持たせるか | **持たせない**。`par===3` / `par===5` から導出できる**冗長データ**であり、二重管理は `2026-08-20-npdc-par.md` §2.1 が退けた B 案（同期ポイントを増やす）そのもの。単一ソース = `nines[].par` を守る |

→ 受け入れ条件 §10-B に「読込直後、追加操作なしで NPDC カードに Par3/Par5 のホールが並ぶ」を入れて**回帰で守る**。

### 3.3 積み残し（本設計のスコープ外・§15 Q2）

実在コースは Par3×4・Par5×4（par 72）が典型で、**NP が4ホール・DC が4ホールになる**。現行は個数制限なし（`npdc-par.md` §1-3 でユーザー確定済み）。対象ホールを個別に OFF する機能は **§3.6 の改訂を伴う load-bearing 変更**なので本設計では扱わない。

### 4.2 なぜ 9H 単位に一本化するか（「18H直接」も許す案を採らない理由）

日本のゴルフ場は **27H（9H×3）・36H（9H×4）が珍しくなく**、コンペはそのうち2つを組み合わせて18Hをラウンドする。幹事Excel の `score` シートも `W1..W9` / `N1..N9` の**2ブロック構成**だった（`2026-08-31-host-excel-analysis.md` §50-61: par 実測 `W1..W9 = 5,3,4,4,4,4,4,3,5`(36) / `N1..N9 = 4,5,3,4,4,3,5,4,4`(36) → 72）。

`par[18]` 固定（rev.1）だと 27H のゴルフ場に対して「西→北」「北→東」「東→西」…と**組合せの数だけ別レコード**が要り、同じ9Hのパーを何度も入力・修正することになる。

**決定: 9H単位に一本化する（`par[18]` を持つ形は残さない）。**

| 論点 | 決定 | 理由 |
|---|---|---|
| 「18H直接」も許すか | **許さない**（`courses[].par` は存在しない） | 2形式を許すと **読込・保存・管理UI・migrate の全経路が二重化**する。「`par[18]` と `nines` のどちらが正か」という曖昧さも生む。**バックログ段階＝互換性の負債ゼロ**なので、今一本化するのが最も安い |
| 18H単一構成のゴルフ場 | `nines` が **2つ**（既定名 `OUT` / `IN`） | 保存時に自動でそう作られる（§8.3）。読込UIでも**最初から正しい2つが選ばれている**ので、ユーザーは「読み込む」を押すだけ＝違和感なし（§8.2） |
| ナインが1つだけ（9Hコース） | 許す。OUT/IN 両方に同じナインを選ぶ＝2周 | 特別扱いのコードを書かない |
| 同じナインを2回（西→西） | **許す** | 27Hで「西→西」の18Hラウンドは実在する。両セレクトを独立に全ナイン列挙するだけ＝**排他制御を書かない**（コードが減る）。ただし**上書き保存だけは不可**（§8.4） |
| ナインの個数上限 | なし | 36H（4つ）以上も自然に入る |

### 4.3 項目の採否

| 項目 | 採否 | 理由 |
|---|---|---|
| `courses[].name`（ゴルフ場名） | **採用** | 選択 UI の第1段。読込時に `g.course` の合成に使う |
| `nines[].name`（ナイン名） | **採用（rev.2 で前倒し）** | 「西」「北」「OUT」など。**読込UIの選択肢**と `g.course` の合成（`○○CC（西→北）`）に**即座に消費者がある**＝死にフィールドにならない。9H単位にしたことで自然に持てるようになった |
| `nines[].par[9]` | **採用** | 本体。これだけで NP/DC・規定打数・隠し12抽選の帯分類まで決まる |
| `note` | **採用** | 「バックティー」など同名コースの区別。フリーテキスト1つで十分 |
| `updatedAt` | **採用** | 一覧の既定ソート（新しい順） |
| `id` / `nines[].id` | **採用** | `uid()`。改名しても参照が壊れない（`team.id` の前例） |
| **ホール名表記（`W1..N9`）の表示** | **Phase C**（データも持たない） | ナイン名から `西1..西9` のように**合成できる**ので専用フィールドは不要。ただし**表示**するには score/course/results/roulette の**全ホール表のヘッダ**に手を入れる必要があり、Phase A の数倍の影響範囲。別 Issue（§13） |
| `hidden[18]` | **不採用** | 隠し12は**そのコンペの抽選結果**でありコースの属性ではない。マスタに入れると「前回の抽選が復活する」不正な挙動になる |
| ショート/ロング フラグ | **不採用** | §3.2。`par` から導出できる冗長データ |
| ヤード数・コースレート・HDCP インデックス・ティー区分 | **不採用** | §3 のどの式も参照しない（`parTotal` すら par 合計のみ）。消費者のないデータを持たない。ティー区分は当面 `note` のフリーテキストで運用（§15 Q1 の回答次第で見直し） |
| ペリア係数・上限などの集計ルール | **不採用** | コースではなく**コンペの設定**（`g.periaCoef` 等）。混ぜない |
| `g.courseRef` | **採用** | 「上書き保存」の宛先と「どこから読んだか」の表示のためだけの**弱参照**。計算は一切参照しない。マスタ削除で dangling になっても `find` が `undefined` を返す＝未リンク扱いで無害（`custom-match.md` §4.1 の孤児エントリ放置と同じ方針） |

### 4.4 migrate / 既存データ

`js/state.js` の `migrate(s)` に以下を足す。

```js
if(!Array.isArray(s.courses)) s.courses=[];                       // コースライブラリ（2026-09-06-course-master.md §4）
s.courses.forEach(c=>{                                            // ★防御的正規化：par は必ず 9 要素
  if(!Array.isArray(c.nines)) c.nines=[];
  c.nines.forEach(n=>{ if(!Array.isArray(n.par)) n.par=[];
    while(n.par.length<9) n.par.push(4); if(n.par.length>9) n.par=n.par.slice(0,9); });
});
// 既存 (s.games||[]).forEach(g=>{ ... }) の中に1行
if(g.courseRef===undefined) g.courseRef=null;
```

- `newGame()` に `courseRef:null` を追加（`course:""` の直後）。
- **`par` を必ず9要素に正規化する**のは load-bearing 上の要点。他人が編集した JSON を取り込んだときに `n.par.length` が 9 でないと、展開結果 `g.par` の長さが 18 でなくなる。`js/calc.js` の全ループは **18固定**（`sum(a,0,18)` / `hidden` 18要素との添字対応）を前提にしているので、**ここだけは §3 に波及しうる**。migrate と読込の**二重**で防ぐ（§8.2）。
- **既存ゲームからのマスタ自動生成はしない**（決定）。理由:
  1. `g.course` は自由入力の文字列で、空・表記ゆれ・テストデータ（`テスト国際CC`）が混在する → **ノイズだらけのマスタ**になる。
  2. migrate が**データを増やす**のは非可逆で、バックアップ再取込のたびに重複が増える（migrate は冪等であるべき）。
  3. 代替が1タップで済む（§8.3 の「このコースを保存」）。
- 旧バックアップ（`courses` なし）の取込は `importData` → `migrate(s)` で補完される＝**`js/backup.js` は無改修**。`exportData` は `state` 全体を JSON 化するので `courses` は自動的に含まれる（`js/backup.js:2`）。

## 5. 9H×2 → 18H の展開（唯一の変換ロジック）

```js
/* ライブラリの2ナインを18ホールへ展開。g.par は今までどおり「18要素のフラット配列」（§3 非接触の前提） */
function clibExpand(out, inn){ return out.par.slice(0,9).concat(inn.par.slice(0,9)); }   // 必ず length 18
```

- **`g.par` の形は一切変えない。** ナイン構造はライブラリ側にだけ存在し、コンペに入る瞬間にフラット化される。
- 逆変換（保存時）は `g.par.slice(0,9)` / `g.par.slice(9,18)`。
- **数値例**（幹事Excel の実測値・`host-excel-analysis.md` §60）:

```
西 = [5,3,4,4,4,4,4,3,5]  (36)
北 = [4,5,3,4,4,3,5,4,4]  (36)
西→北 : g.par = [5,3,4,4,4,4,4,3,5, 4,5,3,4,4,3,5,4,4]  合計 72
        → niapinHolesOf = [1,7,11,14]      (2H,8H,12H,15H = Par3×4)
        → draconHolesOf = [0,8,10,15]      (1H,9H,11H,16H = Par5×4)
北→西 : g.par = [4,5,3,4,4,3,5,4,4, 5,3,4,4,4,4,4,3,5]  合計 72（同じゴルフ場・別の組合せ）
        → niapinHolesOf = [2,5,10,16] / draconHolesOf = [1,6,9,17]
西→西 : g.par = [5,3,4,4,4,4,4,3,5, 5,3,4,4,4,4,4,3,5]  合計 72（同一ナイン2周も可）
```

## 7. 影響範囲 — **§3 計算仕様に非接触である証明**

`g.par` を読んでいる箇所は以下がすべて。いずれも**レンダリング時／集計時に `g.par` を読むだけ**なので、値の由来（手入力か、ライブラリ展開か）で挙動は変わらない。＝「幹事が18個の数字を手で打った」場合と**完全に同一**。

| 参照箇所 | 役割 | マスタ導入の影響 |
|---|---|---|
| `calc.js:2` `parTotal` | 規定打数（ペリア HDCP の基準） | なし |
| `calc.js:14` `periaHdcp` | ダブルパーカット `2*g.par[i]` | なし |
| `calc.js:33,36` | ステーブルフォード／オリンピックの対パー差 | なし |
| `calc.js:98,104` | Vegas の上限・バーディ判定 | なし |
| `calc.js:152` `uvHdcpA` | 大学対抗 HDCP の隠し12合計 | なし |
| `state.js:72-73` `niapinHolesOf` / `draconHolesOf` | NP/DC 対象ホール導出 | **狙いどおり自動追従**（§3） |
| `course.js:33` `pickHidden12` | 隠し12の帯別抽選 | なし（`randomHidden()` を押したときだけ走る） |
| `course.js:57` `courseGrid` / `score.js:26` / `results.js:187-189` / `roulette.js:93,181` | Par 行の表示 | なし（再描画で新しい値が出るだけ） |
| `testdata.js:202-238` | シード生成 | なし（`newGame()` 経由＝`courseRef:null`。**testdata.js は無改修**） |

| 条件 | 表示 |

### 8.5 管理（`<details>` 内）

| 操作 | 挙動 |
|---|---|
| ゴルフ場名／メモの変更 | `onchange="clibSetVenue('<cid>','name',this.value)"` → `updatedAt` は**更新しない**（パーの版とは別物）。読込済みコンペの `g.course` は**追随しない**（コピー方式・§8.6） |
| ナイン名の変更 | `onchange="clibSetNine('<cid>','<nid>','name',this.value)"`。空にすると表示は `clib.nineNo` |

### 8.6 コピー方式（決定・rev.1 から変更なし）

**読み込んだ後にコンペ側でパーを編集しても、ライブラリは変わらない。** 逆にライブラリを編集してもコンペは変わらない。反映は**明示的な「上書き保存」だけ**。

- 理由: ラウンド当日の「17番のパーが違った」は**そのコンペの訂正**であって、ライブラリの改訂とは限らない。参照方式（`courseRef` を計算が引く）にすると、ライブラリを1つ直しただけで**過去の全コンペの HDCP と順位が遡って変わる**。これは絶対に避ける。
- 副次効果: 既存の全計算コードが `g.par` を読むだけで済む＝ `calc.js` 無改修（§7）。

### 8.7 その他の連動

- `dupGame()`（`basic.js`）は JSON 深コピー → `courseRef` も複製される。複製先も同じライブラリ項目にリンクしたまま＝仕様として正しい。**改修不要**。
- `deleteGame()` はゲームを消すだけ。ライブラリは残る。**改修不要**。
- 一覧の並び: `updatedAt` 降順（新しい順）。同日は配列順。**ソート UI は作らない**。

## 10. 受け入れ条件

**A. 保存・読込（要件1）**
1. コースタブ先頭に「コースライブラリ」カードが出る。ライブラリが空のときは `clib.empty` が出る。
2. パーを入力した状態で「このコースを保存」（保存先＝新しいゴルフ場）→ ゴルフ場セレクトに出て、ナインが `OUT` / `IN` の2つできる。管理表で「西」「北」に改名できる。
3. **27H シナリオ**: 上記の続きで、コンペのパーを「東→西」の並びに直し、保存先に同じゴルフ場を選んで保存 → **後半の「西」は再利用され、前半だけが新しいナインとして追加**される（ナインが3つになる。**4つにならない**）。
4. 別のコンペを新規作成 → ゴルフ場「○○CC」・OUT「西」・IN「北」を選んで「読み込む」→ confirm を OK → **18ホールのパーが `西.par + 北.par` と一致**し、ヘッダと基本設定の「コース」欄が `○○CC（西→北）` になる。
5. **18H単一構成**（ナインが2つのゴルフ場）を選ぶと、OUT/IN のセレクトが**既定で正しい2つ**になっており、そのまま「読み込む」を押すだけで済む。
6. **同じナインを2回**（西→西）も選べて読み込める。そのとき「上書き保存」は**出ず**、`clib.updateNg` の注記が出る。
7. 読込後にコンペのパーを1つ変えても**ライブラリの値は変わらない**（管理表のパー合計が変わらない）。
8. 「上書き保存」はリンク中かつ OUT≠IN のときだけ表示され、押すと2ナインの par と更新日だけが変わる（名前・メモは保持）。
9. 管理表でゴルフ場名／メモ／ナイン名をインライン編集でき、ナイン単位・ゴルフ場単位で削除できる。**削除しても、そのコースを読み込んだ既存コンペのパー・スコア・順位は一切変わらない**。

**C. データ・非回帰**
12. `g.hidden` は読込・保存のどの操作でも変化しない（読込前後で隠しホールのチェック位置が同一）。
13. **`g.par.length === 18` が常に保たれる**。`nines[].par` が9要素でない壊れた JSON を取り込んでも、migrate の正規化と読込時ガードで 18 が崩れない。

### 12.3 採らない理由（この順に効く）

1. **APIキーを置く場所がない（決定的）。**
   76-Club は GitHub Pages 配信の**静的サイト**で、サーバー側の処理が1行も存在しない。ブラウザに配る JS にキーを書けば、**ソース表示・DevTools のネットワークタブで誰でも読める＝公開**である。「ユーザーが自分のキーを入力する」BYOK 方式も、保管先が `localStorage`（**キーを増やせない**制約）か `golfCompe_v1`（**バックアップ JSON に秘密が混ざり、JSON を人に渡せなくなる**）しかなく、どちらも詰む。
   → これは並走設計 `2026-09-06-data-import.md` §6.2-2 が写真OCRの外部 API を退けたのと**まったく同じ理由**であり、本アプリの設計制約として一貫させる。

2. **CORS が保証されない。**
   CORS はブラウザ側で強制される仕組みで、`Access-Control-Allow-Origin` は**呼び出し側ではなくAPI 側のレスポンス**に含まれていなければならない。API がそれを返さない限り、**クライアント側の工夫では回避できず、自前のプロキシサーバーが要る**（＝バックエンドを持つことになる）。上表のどのサービスも「ブラウザから直接叩ける（CORS 対応）」とは公表していない（**未確認**）。一般に、この種の従量課金 API は**キー保護のためサーバー間通信を前提**にしている。

3. **日本のカバレッジが未確認、かつ表記の照合が難しい。**
   グローバル系はどこも日本の網羅度を公表していない。Golf Intelligence は自ら **US/UK が最も強い**と述べ、収録確認は個別問い合わせと案内している。仮に収録されていても、**日本語のゴルフ場名（略称・「CC」「GC」「カントリー倶楽部」の表記ゆれ）**でヒットさせる照合が必要で、ここが実務上いちばん壊れる。さらに本設計の肝である**「西/北/東」といったナイン単位の構成**が API 側でどう表現されているかは、どのサービスも公表していない（27H・36H は日本に多い構成で、US/UK 中心のデータモデルでは 18H 前提のことが多い）。

4. **日本を確実にカバーする楽天GORA API は、用途が違う。**
   GORA の3 API（ゴルフ場検索／ゴルフ場詳細／プラン検索）は**予約・空き枠のための API**で、ホールごとの par を返すという記載は確認できなかった。加えて `applicationId` が必須（＝理由1と同じ問題）で、取得データの保存・再配布の可否は利用規約の確認が要る（**未確認**）。**日本のゴルフ場データを par 単位で提供する公開 API は、調べた範囲では見つからなかった。**

5. **オフラインで動く性質が壊れる。**
   ゴルフ場のクラブハウスは電波が弱いことが多く、76-Club は「静的サイト＋localStorage で通信不要」がそもそもの強み。コース設定は当日その場でやることもある。**取込のためだけに通信必須の経路**を作るのは筋が悪い（`data-import.md` §6.2-1 と同じ判断）。

6. **費用。** 明示されている商用価格は **Starter $399/月**（Golf Intelligence）。趣味のコンペアプリが年 5,000 ドル規模を負担する理由はない。無料枠のあるサービスも、回数制限と規約の確認が要る。

7. **規約（データの保存可否）。** 取得データをアプリ内（localStorage）に保存し続けてよいかは各社の規約次第。golfapi.io は「取得したコースデータを保存・キャッシュしてよい」旨を記載しているが、他社（とくにライセンス型の iGolf / GolfLogix）は**再配布・保存に制限があるのが通例**で、本アプリの JSON バックアップ（ユーザー間で渡し合う）と衝突しうる。**未確認のまま作り始めてはいけない領域**。
