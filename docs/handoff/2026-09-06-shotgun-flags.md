## 1. 要件（ユーザー原文・2026-09-06「ゆる募」）

> 【ゆる募】コース上でモバイルで使う前提での話です。過去にショットガンの幹事をした時はドラニアの旗を誰に渡して誰に回収してもらうかが複雑でした。当日朝にスタートホールが分かったら、国分表に各組のスタートホールをExcel入力し、Par3と5を最初と最後に通る組のエチケットリーダー名を表示するように準備しました。画面キャプチャして皆さんお願いします〜でした。モバイルで各組にスコアを入力してもらうときは、これを対応したいですね。

### 1.2 幹事の困りごと（本機能が解く問題）

当日朝、スタートホールが判明してから始球式までの**15〜30分**で、対象ホール（典型的に Par3×4＋Par5×4＝**8本の旗**）それぞれについて「誰に渡すか／誰が回収するか」を全部決めて周知する必要がある。手計算は巡回順の mod 18 を8回×2＝16回やることになり、朝の混雑時にはミスが出る。

**本機能の成果物 = 各組のスタートホールを入れるだけで、8行の受け渡し表が自動で出る。それをキャプチャして配る。**

## 2. 運用モデル（旗が物理的にどう流れるか）

```
  朝の集合（始球式前）              ラウンド中                    最終ホール後
  ┌──────────────┐                                            ┌────────────┐
  │ 幹事が旗を配る │ ──→ 最初に通る組が対象Hに設置 ──→ 各組が    │ 最後に通る │
  │ （8本）        │      （自分の名札を置く）        更新しながら │ 組が回収   │
  └──────────────┘                                  通過        │ →幹事へ返却│
                                                                └────────────┘
```

**重要な帰結**: 旗を「渡す」のは常に**朝の集合時**（全組が同時に散るため、途中で手渡す機会がない）。つまり本表は **朝に1回見れば足りる静的な表**であり、リアルタイム同期は不要 → **単独で先に出せる**（§13）。

- 対象ホールから**スタートする組**（オフセット0）＝その組が最初。朝に旗を渡す点は他と同じ。
- **最後に通る組**は、対象ホールがその組の 18 ホール目（オフセット17）になることが多い＝**ラウンド終了と同時に回収**。自然な運用。

### 3.2 案1 → 案2 の移行コスト（評価）

候補 J が後から入る場合、`g.parties = [{id, name, memberIds, ...}]` を新設し、`migrate()` で以下を行う:


- **捨てるデータはゼロ**（`g.shotgun.groups` は `g.parties` の真部分集合）。

## 4. 計算仕様（純関数・§3 非接触）

> ⚠ **本節は正本 §3（計算仕様）ではない。** スコア・HDCP・ネット・勝ち点のどれにも触れない。
> §3 の関数群（`periaHdcp`/`netScore`/`computePoints`/`teamWinPoints` …）を**読みも書きもしない**。§5 で非接触の根拠を示す。

### 4.1 基本式

巡回長 `HN = g.par.length`（現行は常に 18。将来 9 ホールモードが来ても式は不変）。

組がスタートホール `s`（1-based）から出るとき、ホール `h`（1-based）に到達する順番（**オフセット**、0-based）は:

```
off(h, s) = (h - s + HN) mod HN
```

- `off = 0` … その組の**1ホール目**（＝スタートホールそのもの）
- `off = HN-1` … その組の**最終ホール**

全組が同時にスタートし同ペースで進むので、**オフセットが小さい組ほど早くそのホールを通る**。

```js
// 参照実装（js/shotgun.js に置く。ここが「組の配列をどこから読むか」を閉じる唯一の場所）
function sgGroups(g){ return (g.shotgun && g.shotgun.groups) || []; }        // ← 候補J移行時はここだけ差し替える
function sgOff(hole1, start1, HN){ return (hole1 - start1 + HN) % HN; }
```

### 4.2 対象ホールの導出（★既存関数をそのまま使う）

```js
const NP = niapinHolesOf(g);   // js/state.js:72 … Par3 の 0-based index 配列
const DC = draconHolesOf(g);   // js/state.js:73 … Par5 の 0-based index 配列
```

**新しい導出は作らない。** 表示は `index+1` で 1-based にする（既存 `js/course.js` の NPDC カードと同じ変換）。
行の並びは **ホール番号昇順（NP/DC 混在）**、種別はピルで示す（§6.2）。

### 4.3 「最初／最後に通る組」と同着処理

```js
// 戻り値: null（スタートホール入力済みの組が0件）または
//         { first, last, firstTie, lastTie }   first/last は {idx, no, startHole, off}
function sgFirstLast(g, hole1){
  const HN = g.par.length;
  const a = sgGroups(g).map((gr,i)=>({idx:i, no:i+1, startHole:gr.startHole}))
                       .filter(x=>x.startHole!=null)
                       .map(x=>({...x, off:sgOff(hole1, x.startHole, HN)}));
  if(!a.length) return null;
  const mn = Math.min(...a.map(x=>x.off)), mx = Math.max(...a.map(x=>x.off));
  const F = a.filter(x=>x.off===mn).sort((x,y)=>x.no-y.no);   // 同着は組番号昇順
  const L = a.filter(x=>x.off===mx).sort((x,y)=>x.no-y.no);
  return { first:F[0], last:L[L.length-1],
           firstTie:F.length>1?F.map(x=>x.no):null,
           lastTie: L.length>1 ?L.map(x=>x.no) :null };
}
```

**同着（同じスタートホールの組が複数＝1A/1B 方式）のタイブレーク**:

| 側 | 採用する組 | 根拠 |
|---|---|---|
| 最初（渡す） | 同着のうち **組番号が最小** | 同じホールから出る2組は、**組番号の小さい方が先にティーオフする**のが慣例。実際に先に通る |
| 最後（回収） | 同着のうち **組番号が最大** | 同上。番号の大きい方が後から通る＝実際に最後 |

→ **単一の組を指名できる**（表の各セルは1組・1名）。同着が存在する行には `＊` を付け、表の下に注記1行（`sg.tieNote`）を出す。

### 4.4 リーダー名の解決

```js
function sgLeaderName(gr){
  if(gr.leaderPid){ const p=state.players.find(x=>x.id===gr.leaderPid); if(p) return p.name; }
  return gr.leaderName || '';        // 空なら表示側で '—'
}
```

- pid の選手がマスタから消えていた場合 → `leaderName` → `—` の順にフォールバック。**組番号は常に出るので運用は破綻しない**。

### 4.5 エッジケース一覧（すべて §5 で実測）

| ケース | 挙動（決定） |
|---|---|
| 組が対象ホールから**スタート**（`off=0`） | その組が「最初」。旗は朝の集合で渡す（他と同じ）。特別扱い不要 |
| **同じスタートホールに2組**（1A/1B） | §4.3 のタイブレーク。行に `＊`＋注記 |
| **18組未満**（例 12組・スタートホールに欠番） | 式は不変。欠番ホールでは「最小の正のオフセットを持つ組」が最初になる。破綻しない |
| **9ホールスタート**（1〜9H からのみ出発） | 同上。`HN` は `g.par.length`＝18 のまま（アプリの18ホール前提と一致） |
| **18組超**（20組など） | 必ずスタートホールが重複 → §4.3 で解決 |
| `startHole` **未入力**の組がある | その組を計算から**除外**し、表の下に `sg.missing`（未入力の組番号一覧）を警告表示 |
| **全組が未入力** | 表を出さず `sg.needStart` の空状態 |
| **1組しかない** | first と last が同一組 → セルに `sg.same`（同一組）タグを出す（回収忘れ注意の合図） |
| **Par3/Par5 が1つもない** | `sg.noTarget` の空状態（既存 `game.npdcNone` と同じ思想） |
| **組が0件** | カードは入力の空状態（`sg.empty`）のみ。旗表カードは非表示 |

## 13. 「モバイルで各組にスコア入力」との関係（★切り分け）

ユーザーの原文末尾「モバイルで各組にスコアを入力してもらうときは、これを対応したいですね」について。

### 13.1 本機能は単独で先に出せる — **YES**

| 論点 | 判定 |
|---|---|
| 複数端末の同時アクセスが要るか | **不要**。旗の受け渡しは**朝の集合時に1回**決まる静的情報（§2）。ラウンド中に更新されない |
| 誰が入力するか | **幹事1人**（自分の端末で組とスタートホールを入れる） |
| どう配るか | **スクリーンショット1枚**を LINE 等で共有（ユーザーの実際の運用そのもの） |
| 現行の localStorage 単独運用で成立するか | **成立する** |

→ **本機能は Phase 2（Firebase）に依存しない。今の 76-Club にそのまま載る。**

### 13.2 別テーマとして切り出すもの

| テーマ | 内容 | 前提 | 本設計との関係 |
|---|---|---|---|
| **T1: 複数端末での同時スコア入力** | 参加者/組ごとの端末から入力→幹事画面にリアルタイム反映 | **正本 §5 Phase 2（Firebase Firestore ＋ 匿名Auth ＋ `?room=`）が必須**。現行の `golfCompe_v1` 単独では原理的に不可能 | 独立。本機能の完了を待つ必要はない |
| **T2: パーティ（組）分けの概念** | 全参加者を組に割り当てる。組ごとスコア入力画面 | 単独端末でも可能（L サイズ） | 本機能の `g.shotgun.groups` を `g.parties` に昇格させる形で**上位互換**（§3.2） |
| **T3: 組単位のスコア入力 UI** | 「この組の4人だけ」を大きく表示して入力 | T2 が前提。T1 があるとさらに活きる | 本機能とは独立 |

**推奨順序**: 本機能（M）→ T2（L）→ T1（Phase 2・XL）→ T3。
本機能を先に出すと、T2 の設計時に「組のデータが実際にどう使われるか」の実例が1つ手に入るという副次的な利点がある。
