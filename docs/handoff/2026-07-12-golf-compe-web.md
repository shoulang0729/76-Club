## 1. 背景 / ゴール

ゴルフコンペの集計・運営をスマホから行う。既存OSSに日本式コンペ（ダブルペリア・ニアピン/ドラコン・チーム対抗・女性エブリハンデ）を満たすものが無かったため新規開発する。段階導入：

- **Phase 1（公開済）**: 幹事1台完結。端末内 `localStorage` にデータを保存し、全機能を提供。JSONで書き出し/読み込み。
  → **この設計書の「§3 計算仕様」「§4 データモデル」は Phase 1 で実装済みの正本**。Phase 2 でもロジックを変えずに再利用する。
- **Phase 2（本タスク）**: Firebase を追加し、**参加者全員が各自のスマホからスコア/名前を入力**、幹事の画面と全員の画面がリアルタイム同期。QRコード/リンクで「部屋（コンペ）」に入室。

Phase 1 は既に動くので、Phase 2 の実装は「①Phase 1 を素直な複数ファイル構成へリファクタ」→「②Firebase 同期レイヤーを被せる」の2段。

## 3. 計算仕様（★正本・ロジックを変えないこと）

すべて `src/calc.js` の純粋関数として持つ。`par[i]`（0..17）、`scores[pid][i]`（打数 or null）、`hidden[i]`（真偽・隠しホール）を入力にとる。

### 3.1 ダブルペリア（新ペリア）ネットHDCP
```
規定打数 parTotal = Σ par[i]                        （通常72）
隠し合計 H       = Σ (i が隠しホールのときの scores[pid][i])
HDCP           = (H × 1.5 − parTotal) × periaCoef
HDCP < 0 なら 0、HDCP > periaCap（設定時）なら periaCap でクリップ
HDCP は小数第1位に丸め
```
- `periaCoef`（既定 0.8）、`periaCap`（既定なし=null）は**ゲームごとに設定**。隠しホールは12ホール選ぶ（ランダム選択ボタンあり）。
- **★§11.1（2026-08-16 Issue#2）で上書き**：ランダム選択ボタンはPar配分（ロング2/ショート2/ミドル8＝隠しPar合計48）で選ぶ。
- **★§11.2（2026-08-16 Issue#3）で上書き**：`H`（隠し合計）は**エブリ適用前の生スコア（実打数）**で集計する（新ペリアの慣例＝実際に叩いた打数からハンデを推定）。エブリはペリア計算に混ぜない。

### 3.2 女性エブリハンデ
- ゲーム設定で「適用ON/OFF」＋「エブリワン(−18) / エブリツー(−36)」を切替。
- 対象は `gender === 'F'` の選手のみ。
```
womenEvery(pid) = (適用ON かつ 女性) ? (type===1 ? 18 : 36) : 0
```

### 3.3 グロス個人戦 / ネット個人戦
```
gross(pid)    = Σ scores[pid][i]
effGross(pid) = gross(pid) − womenEvery(pid)      # ← グロス個人戦のランキングに使う（女性エブリ反映）
net(pid)      = effGross(pid) − periaHdcp(pid)     # ← ネット個人戦。女性エブリはネットにも波及
```
- グロス個人戦・ネット個人戦とも**小さいほど上位**。同スコアは同順位。
- **★§11.2（2026-08-16 Issue#3）で上書き**：`effGross` のエブリ控除を「各ホール−1/−2の実額合計（＝表示と同一基準）」に統一し、`enteredCount/18` の段階反映式を廃止。`periaHdcp` は生スコア基準のまま（上記§3.1）。二重控除しない。

### 3.4 追加ゲーム（各ゲームの ON/OFF はゲーム設定）
- **ステーブルフォード**（グロス基準・高いほど良い）: 各ホール `d = 打数 − par`。`d≤−3:5, −2:4, −1:3, 0:2, 1:1, それ以上:0` を合計。
- **オリンピック（陣取り・高いほど良い）**: 各ホール `d≤−3:10, −2:6, −1:4, 0:1, それ以上:0` を合計。
- **キャロウェイ方式**（18H入力完了者のみ・ネット＝小さいほど良い）: グロスから控除ホール数テーブルで最悪ホール（**17・18番を除く**1〜16番から）を控除＋補正。実装はプロトタイプ `callawayHdcp()` を踏襲。
- **握り/ナッソー**（前半OUT/後半IN/トータルのネット・各9H）: 各9Hのネット = 9H素点 − periaHdcp/2 − womenEvery/2。3セクションそれぞれ小さいほど良い。
- **ベスト2ボール**（チーム内ネット上位2名の合計・小さいほど良い）。

### 3.5 チーム対抗
- **グロス対抗** = Σ effGross（メンバー）。小さいほど良い。
- **ネット対抗** = Σ net（メンバー）。小さいほど良い。
- **ホールバイホール**: 各ホールでチーム合計打数（そのホールを入力済みのメンバーの和）が**最少のチームがそのホールを取る**。同点は山分け（`1/同点チーム数`）。取ったホール数の合計で勝敗。
- **ラスベガス（Vegas）**: 2人1組の2スコアを2桁合体→フリップ→点差累積（**★§11.11 が正本**・2026-08-16追加）。
- **★§11.15（2026-08-20・確定）で配点方式を上書き**: 種目別チーム配点（勝ちチーム各員◯pt）を**廃止**し、各チーム種目は「総合で勝ったチームに勝ち点1（同点は山分け）」→勝ち点合計の**総合順位**に `points.teamRankPts`（既定 [10,5]）をチーム各員へ配分。**ニアドラ（NP＋DC獲得本数のチーム合算）を1種目として追加**。**ラスベガスも勝ち点種目**（点差の独立集計は維持し、`vegasHoleNet` の符号＝ホール勝敗数で判定）。各種目の勝敗値の計算式（本節）は不変。詳細は `docs/handoff/2026-08-20-team-points.md` が正。

### 3.6 ニアピン / ドラコン（個人賞）
- ~~ゲーム設定で対象ホールを指定（青=ニアピン / 赤=ドラコン、トグルで none→NP→DC→none）~~ **★2026-08-20 改訂: 手動指定を廃止。対象ホールはパー設定から自動導出（Par 3=ニアピン / Par 5=ドラコン・個数制限なし・par===3/5 の厳密一致）**。導出は純関数 `niapinHolesOf(g)`/`draconHolesOf(g)`（詳細・前後比較は `docs/handoff/2026-08-20-npdc-par.md` が正）。
- 結果タブで各対象ホールの勝者を選択して記録。配点は**導出対象ホールの勝者のみ**加算（導出対象外ホールに残る勝者記録は保持するが集計・表示から無視＝パーを戻せば復活する非破壊・可逆挙動）。
- ローカルルール注記：**女性はニアピン/ドラコンとも2打目を計測対象にできる**（計算ではなく運用注記として画面表示）。この判定に選手の性別（男/女）を使うため、選手マスターに性別が必須。
- **★§11.15（2026-08-20・確定）追補**: 個人賞（1本あたり◯pt）は**不変のまま**、獲得本数のチーム合計を新種目「ニアドラ」としてチーム戦の勝ち点にも算入する（詳細 `docs/handoff/2026-08-20-team-points.md` §3.3.1）。

## 5. Phase 2：全員同時入力（Firebase・本タスクの主眼）

### 5.1 目標
1. 幹事が「部屋（コンペ）」を作成 → **QRコード/共有リンク**が出る。
2. 参加者は QR/リンクを開き、**名前を入力してすぐ参加**（アカウント登録なし）。
3. 各自が自分（や同組）のスコアを入力 → **全員の画面がリアルタイムに同期**。
4. オフラインでも入力でき、復帰時に自動同期（Firestore のオフライン永続化）。

### 5.2 技術選定
- **Firebase Firestore**（リアルタイム同期・無料 Spark プランで十分）＋ **Firebase Anonymous Auth**（匿名サインインで書き込み主体を識別）。
- 静的フロントは GitHub Pages のまま。Firebase SDK は CDN（`https://www.gstatic.com/firebasejs/…`）から読む（バンドラ不要）。
- Firebase 設定値（apiKey 等）はフロントに埋め込む公開情報で問題なし。**書き込み制御は Firestore セキュリティルールで行う**（§5.5）。
  - ⚠ Firebaseプロジェクト作成（無料）＋ウェブアプリ登録＝**ユーザー（shoulang0729 の Google アカウント）が Firebase コンソールで一度だけ行う作業**。実装者は config の受け口だけ用意し、値は環境に応じ差し込む（`src/firebase-config.js` に公開config、または `?` なしで直書き）。

### 5.3 Firestore データモデル
Phase 1 の `game` オブジェクトを「部屋 = room」に対応させる。ルームコード（6桁英数字・大文字）をドキュメントIDに。

```
rooms/{roomCode}                      // 1コンペ=1ルーム
  meta: { name, date, course, hostUid, createdAt, locked:false }
  config: { par[18], hidden[18], periaCoef, periaCap, womenEvery, formats }
  players/{playerId}: { name, gender, claimedByUid|null }   // 参加者（=選手）
  teams/{teamId}:     { name, memberIds[] }
  scores/{playerId}:  { holes:[18], updatedBy, updatedAt }  // スコアはプレイヤー単位ドキュメント
  prizes/meta:        { niapinHoles[], draconHoles[], niapinWinner{}, draconWinner{} }
```
- **購読単位**: フロントは `rooms/{code}/players`, `/teams`, `/scores`, `config`, `prizes` を `onSnapshot` で購読 → 変更が来たら §3 の計算を再実行して結果を再描画。
- 計算（§3）は**クライアント側**でそのまま実施（サーバー不要）。Firestore は素点と設定の共有だけを担う。

### 5.4 入室フロー（QR / リンク）
- ルーム作成時に共有URL `https://shoulang0729.github.io/76-Club/?room=ABC123` を生成し、**QRコード表示**（QR生成は軽量ライブラリ CDN、例：`qrcode` / `qrcodejs`）。
- URLを開くと匿名サインイン → `?room=` を読んでルーム購読 → **名前入力モーダル**。既存の未claim playerを選ぶ or 新規追加 → その player を自分（uid）に紐付け（`claimedByUid`）。
- ロビー画面：参加者一覧・自分の担当プレイヤー・「スコア入力」導線。

### 5.5 セキュリティルール（Firestore Rules・要点）
- 誰でも匿名サインイン可。**ルームコードを知っている人だけ**そのルームを読み書きできる（コードが実質の合言葉）。
- 書き込みは匿名認証済み（`request.auth != null`）に限定。
- `meta.hostUid` のみ `meta.locked`（締切）・`config`・`prizes` を変更可。締切後（`locked==true`）は一般ユーザーの `scores` 書き込み禁止。
- スコア改ざん抑止：一般ユーザーは**自分が claim した player の `scores` のみ**書き込み可（`resource`/`request` で playerId と claim を突合）。幹事は全 player 可。
- 具体ルールは実装時に `firestore.rules` として起こし、handoff にレビュー観点を追記（本タスクのPRに含める）。

### 5.6 Phase 1 との両立
- **URLに `?room=` が無ければ Phase 1（ローカル単独）モードで従来どおり動く**こと。Firebase 初期化はルームモード時のみ。
- 幹事は「この端末のローカルゲームを部屋として公開」ボタンで Phase 1 の game を room に書き出せると理想（任意・時間があれば）。

### 5.7 くじ引き（将来拡張・今回スコープ外）
今回ユーザーは選択なし。将来 `rooms/{code}/draws` に「組み合わせ抽選 / チーム分け / スタート順」を置き、参加者リストをシャッフルして結果を全員に共有する設計余地を残す。実装は別タスク。

- `gender`（`"M"|"F"`）は残す＝ニアピン/ドラコン2打目注記の表示にのみ使用（計算には使わない）。
- **移行**: 旧データに無ければ `load()` の `migrate()` で既定値を補完。

### 10.3 賞金ポイント配分（新規）
- `game.points`: 各競技の順位別配点（配列）。既定 `net/gross/stableford/olympic/callaway/nassauTotal=[5,3,1]`、`teamGross/teamNet/holeByHole/best2ball=[3]`、`niapin/dracon=2`（1回あたり数値）。**幹事がアプリ内で自由編集**（カンマ区切り入力）。
- `game.prizePool`: 賞金総額（円・整数）。
- **集計** `computePoints(g)`: 有効な各競技で `ranked()`（同スコア同順位）を作り、`points[競技][rank-1]` を加点。個人賞は勝者に `points.niapin/dracon` を回数分。チーム戦は勝ちチームの**各メンバー**に順位別点を加点。
- **配分** `computePayout(g)`: `payout[pid] = round(prizePool × pts[pid] / Σpts)`。ポイントは上限なし＝稼いだ比率で固定総額を山分け。結果タブに「選手／獲得pt／配分額¥」を表示。

### 11.2 エブリ×ダブルペリアの計算順序統一【設計案・Issue#3・§3.1/§3.2/§3.3 上書き】
**慣例調査の結論**：新ペリア（ダブルペリア）のHDCPは **隠しホールの「実際に叩いたグロス（生スコア）」から** 算出するのが普遍的な慣例（`(隠し合計×1.5−72)×係数`）。エブリハンデは新ペリアとは**独立した別のハンデ制度**であり、慣例上ペリア計算の素点には混ぜない。エブリを先に各ホールへ適用してから隠し合計を採ると、隠し合計が縮んでペリアHDCPが目減りし（エブリの恩恵とペリアの恩恵が部分的に打ち消し合う）非標準になる。
出典: [みんなのゴルフダイジェスト](https://www.golfdigest-minna.jp/_ct/17320680) / [Honda GOLF](https://www.honda.co.jp/golf/column/20100610/) / [Golf Signal](https://golf-signal.jp/shin_peoria_system/)。

したがって**現状の「ペリアは生スコア基準」という計算方針は慣例的に正しい**。真の不整合は「エブリ控除の実装方式が計算系（`womenEvery = full × enteredCount/18` の段階反映）と表示系（各ホール−1/−2）でズレていること」にある。修正はペリアの基準を変えず、**エブリの表現をホール単位に一本化**する。

- **決定した計算順序（統一後）**:
  1. `periaHdcp(pid)` … **生スコア（エブリ適用前・実打数）**の隠しホール合計から算出。**変更なし**（§3.1 の式そのまま）。
  2. `everyStrokes(pid)` … `Σ evPer(g,pid)`（開封/入力済みホールについて各ホール −1（every1）/ −2（every2）を実額合計）。**`enteredCount/18` の段階反映式は廃止**し、`adjHole`/`adjArr`（§10.28 の表示基準）と同一の合計にする。→ `womenEvery(pid)` はこの `everyStrokes(pid)` を返すよう置換。
  3. `effGross(pid) = gross(pid) − everyStrokes(pid)` … 全18H入力時は従来どおり every1=−18 / every2=−36 と一致。表示のスコア表「計」と完全一致（乖離解消）。
  4. `net(pid) = effGross(pid) − periaHdcp(pid)` … 二重控除なし（エブリはeffGrossで1回だけ、ペリアは生スコア基準で独立）。
- **波及関数の統一**（すべて `everyStrokes` のホール単位基準へ）:
  - 握り/ナッソー `net9`（:712）: `9H素点 − periaHdcp/2 − （その9Hのevery実額）`。従来の `womenEvery/2` を「当該ハーフのエブリ実額合計」に置換。
  - キャロウェイ・ステーブルフォード・オリンピック等は**生スコア基準のまま**（エブリ非適用）。現状踏襲＝変更しない。
  - ルーレット比較（§10.27/§11.3）は既に各ホール−1/−2の実質スコア基準＝この統一と整合。変更なし。
- **触ってはいけない点の再確認**: ペリア係数・上限クリップ・符号は不変。`womenEvery` という**関数名/フィールド名は互換維持**（中身の算出方式のみ差し替え）。`game.womenEvery.enabled` と `player.everyType`（none/every1/every2）のキーは load-bearing。
- **受け入れ条件（前後比較必須）**: 全18H入力時のネット順位・配分・握り・次回幹事が現行と一致（満額時は数値不変）／リビール途中（一部ホールのみ開封）で「スコア表の計」と「ネット計算に使うeffGross」が常に一致／エブリ選手のペリアHDCPが生スコア基準で変わらないこと。
- **運用**: 本項は §3（load-bearing）の変更。**実装着手前にユーザー最終OK**を取り、テストデータで前後差分を提示してから反映する。

### 11.8 表示モード＝ライト/ダーク（トークン値上書き・全画面反転）【設計案・確定方向・Issue#22／#15を上書き】

### 11.11 ラスベガス（Vegas）ゲーム追加【確定・Issue#19・§3.5チーム対抗を拡張】
**ユーザー確定（2026-08-16 フォーム回答）**: ①**3チーム以上は総当たり**（各対戦の点差を合算）②**フリップ=バーディ以上で相手の数字を反転**（標準）③**各ホールにスコア上限（ダブルパー止め）を設けてから合体** ④**点差を累積してVegas独自の合計で勝敗**（既存の賞金ポイント配分には入れない）。
**★§11.15（2026-08-20・確定）で追補**: 上記④の点差独立集計は維持したまま、**ホール勝敗数（`vegasHoleNet` の符号）でチーム戦の勝ち点1種目**にもなる（計算関数は不変・詳細 `docs/handoff/2026-08-20-team-points.md` §3.3.2）。

**基本**: 2人1組チームの各ホールのスコアを2桁に合体し、対戦チーム同士で数字の小さい方が差分を得る。既存の**チーム対抗ゲーム群**（グロス対抗/ネット対抗/HBH/ベスト2ボール）と同じ枠＝`formats.vegas` として `renderTeams` にカード追加。

**基準（重要・2系統。各々既存の慣例に準拠）**:
- **数字（2桁）に使うスコア＝「エブリ適用後グロスにダブルパー上限」**：`vAdj(g,pid,i)=min(adjHole(g,pid,i), 2*par[i])`（他チーム戦=調整後グロス基準 §10.28 と整合。上限で大叩きの暴発を抑制＝ユーザー指定③）。
- **フリップ発動の「バーディ判定」＝生スコア vs par**：`raw−par ≤ −1`（ステーブルフォード/オリンピック §3.4 と同じ生スコア基準。エブリで容易に発動しないようにする）。
- ※この2系統の割り当ては設計判断（各々に既存準拠あり）。番号も生にしたい等あれば1行で変更可。

**計算仕様（新規の純粋関数・`src/calc.js`）**:
```
vAdj(g,pid,i)      = min(adjHole(g,pid,i), 2*par[i])   （未入力は null）
vegasBase(g,T,i)   : チームTの2メンバーの vAdj を取り、両方入力済みでなければ null。
                     lo=min, hi=max → base = 10*lo + hi
vegasFlip(g,T,i)   = 10*hi + lo                         （大きい方を先頭＝悪化）
vegasBirdie(g,T,i) : メンバーいずれかが (生スコア入力済み かつ raw−par ≤ −1) なら true
vegasHoleNet(g,A,B,i):
   nA0=vegasBase(A), nB0=vegasBase(B); どちらか null ならそのホールは対象外(null)
   Abird=vegasBirdie(A,i), Bbird=vegasBirdie(B,i)
   nA = Bbird ? vegasFlip(A,i) : nA0      # 相手(B)がバーディ→自分(A)の数字を反転
   nB = Abird ? vegasFlip(B,i) : nB0
   return { netA: nB - nA }               # 正=Aが有利(数字が小さい)。netB = -netA
vegasStandings(g):
   資格チーム = memberIds∩participants の人数が「ちょうど2」のチーム
   総当たり（資格チームの全ペア）。各チームの合計 = Σ(対戦相手ごと Σ_holes vegasHoleNet)
   合計が大きいほど上位（＝相手より数字が小さかった＝勝っている）
```
- **暫定/リビール整合**: `renderTeams` に渡る view game（開封切り詰め済み）をそのまま使う＝未開封/未入力ホールは null で自動スキップ（他ゲームと同じ）。
- **ワーク例（Par4）**: A=3(バーディ)&5→base35 / B=4&6→base46。Aがバーディ→**Bを反転** nB=10·6+4=64、nA=35。netA=64−35=**+29**（フリップ無しなら46−35=11。大きく振れるのがVegas）。

**データモデル追加（§4拡張・互換維持）**:

- `game.vegas`: `{ flip:true, cap:'doublePar' }`（フリップON/OFF・上限モード 'doublePar'|'none'）。`migrate()` で既定補完。

### 11.14 投影前提の表示原則【確定・2026-08-20 制定・全画面に適用される設計原則】

**背景**: 本アプリの結果・閲覧系画面は、コンペ後のパーティー会場でプロジェクター/大型モニタに投影し、離れた席の全員が見るのが既定のユースケース。手元スマホ前提のサイズ感で作らない。

**原則**（新規の閲覧系画面は必須。既存画面は個別Issueで順次適用）:
1. **1画面1主役**: その画面で一番知りたい数値・勝敗（順位・スコア・UP差・金額など）を大型表示の主役に据える。基準は投影用大型トークン **`--f-rl-hole`/`--f-rl-name`/`--f-rl-score`**（48/30/44px、@1024: 66/40/64、@1194: 70/44/68、@1366: 76/48/76。§11.10 のルーレット専用枠から**投影用共用トークンに昇格**。値の変更は本節と §11.9/§11.10 の整合を確認してから）。
2. **後方席から読める**: 主役情報は base 44px 以上（`--f-rl-score` 級）＋太字（`--w-bold`）。コントラストは ink/bg トークンで担保し、**面の濃色ベタ塗り禁止**（既存原則）を維持。機能色の意味（勝ち=緑/引分=橙/採用=枠/危険=赤）は大型表示でも保持し、**色だけに頼らず文字を併記**（UP/AS/矢印など・色弱対応）。
3. **幹事の操作UIは投影の邪魔をしない**: 編集・設定・演出操作は `<details>` 折りたたみ・`sm` ボタン・控えめ配置とし、閲覧の主役と視覚的に競合させない。破壊操作の confirm ガードは維持。
4. **演出状態はデータに混ぜない**: 開封・めくり等の演出進行は揮発の表示状態（メモリ変数。例: `revealHoles`）とし、`golfCompe_v1` にも表示状態キーにも保存しない（データ/表示状態の分離原則の系）。

**適用状況**: ルーレット（§11.9〜11.10・先行例）／1 on 1 タブ（§11.13 第2版・適用第1号）。既存他画面の候補リストは `docs/handoff/2026-08-20-1on1-match.md` §13.9。
