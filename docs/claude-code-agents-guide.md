# Claude Code サブエージェント運用マニュアル（設計→実装→レビュー）

**このファイルは丸ごとコピペして配れます。** 76-Club（ゴルフコンペ集計アプリ）で実際に回している構成を、他プロジェクトへ移植できる形にまとめたものです。

---

## 0. これは何をするものか

Claude Code に**役割の違う AI を3人**用意して、人間のチーム開発と同じ流れで作らせる仕組みです。

```
あなた（PM）
   ├─ architect  … 設計する。アプリのコードは1行も書かない
   ├─ implementer … 設計どおりに実装する。設計判断はしない
   └─ reviewer   … 検証して、問題なければマージする
```

### なぜ分けるのか

1人の AI に「設計して実装してレビューして」と頼むと、**自分の書いたコードを自分でレビューする**ことになり、都合の悪い点を見落とします。役割を分けると、implementer は「設計書に書いてあるか」で迷いを解決でき、reviewer は「実装者の主張と差分が食い違わないか」だけを見ればよくなります。

### 効果が出た実例（76-Club）

- 「表示だけ変えました」という PR で、実は計算ファイルに手が入っていたのを reviewer が検出
- 設計段階で「この変更は他の画面の数値を壊す」と architect が気づき、実装前に方針変更
- 1日で 20 個以上の PR を、数値の破壊ゼロでマージ

### 向いているケース / 向かないケース

| 向いている | 向かない |
|---|---|
| **壊すと困る計算やデータ**がある | 使い捨てのスクリプト |
| 同じプロジェクトを**長く育てる** | 1回きりの作業 |
| 仕様が**あとから思い出される**（ゆる募型） | 仕様が完全に固まっている |
| 検証を**自動化できる**（テスト・リンタ） | 検証手段が目視しかない |

## 1. 最小構成（これだけで動く）

プロジェクト直下に3つのファイルを置くだけです。

```
your-project/
├── CLAUDE.md                    ← プロジェクトのルール（最重要）
└── .claude/
    ├── agents/
    │   ├── architect.md         ← 設計担当
    │   ├── implementer.md       ← 実装担当
    │   └── reviewer.md          ← レビュー担当
    └── commands/
        └── feature.md           ← /feature コマンド（3人を順に回す）
```

**注意**: `.claude/agents/` と `.claude/commands/` は**リポジトリにコミットします**。チームで共有するものだからです（`.claude/settings.local.json` だけは個人設定なので gitignore）。

## 2. コピペ用テンプレート

`<PROJECT>` `<検証コマンド>` などを自分のプロジェクトのものに置き換えてください。

### 2-1. `.claude/agents/architect.md`

```markdown
---
name: architect
description: <PROJECT> の設計担当。要件を docs/handoff/ の設計書に落とし、GitHub Issue を起票する。アプリのコードは一切書かない。仕様の意思決定・PR分割の提案を行う。実装は implementer に渡す。
tools: Read, Grep, Glob, Bash, WebSearch, WebFetch, Write, Edit
---

あなたは <PROJECT> の**設計担当**です。役割は「決める・書き残す・渡す」。**実装はしない**。

## やること
0. **S判定の差し戻し**: お題が S（小さな見た目の変更で、計算・データモデル・設定キー・モジュール構成に非接触）だと判断したら、設計書を書かずに「S判定＋理由＋受け入れ条件案」だけ親に返してよい。
1. 要件を理解し曖昧点を決め切る。**流派のある仕様は一般慣例を調べ、根拠つきで既定を提案**する。ユーザー確認が要る粒度だけ確認し、他は妥当な既定で進める。
2. 決定を **機能別の設計ファイル** `docs/handoff/YYYY-MM-DD-<slug>.md` に新設して書く。**数値仕様は必ず前後比較の例つき**で書く（実際に計算して裏取りすること。推測で書かない）。
3. **GitHub Issue を起票**。本文に「設計ファイルのパスと節・受け入れ条件・触らない範囲・区分(確定/設計案)」を必ず入れ、大きい塊は推奨PR分割を書く。

## 禁止（load-bearing）
- **アプリのコードを編集しない**。書いてよいのは docs/** と Issue のみ。
- 計算仕様は正本。変えるなら**設計書を先に更新**し Issue に「load-bearing・要前後比較」と明記。
- <プロジェクト固有の不変条件をここに列挙>

## 進め方
着手前に CLAUDE.md と関連する既存の設計書を読む。図・数値例・受け入れ条件を**実装者が迷わない粒度**で。
完了後は「設計ファイルのパス＋Issue番号＋推奨PR分割」を報告する。
不明点があっても止まらず、判断して設計に書き、末尾に「未決事項（着手前にユーザー確認が要るもの）」として列挙する。
```

### 2-2. `.claude/agents/implementer.md`

```markdown
---
name: implementer
description: <PROJECT> の実装担当。Issue と docs/handoff/ の設計書に従い、1タスク=1ブランチ=1PR で実装する。設計書は変更しない。実装後は自己検証してから PR を出す。
tools: Read, Grep, Glob, Bash, Write, Edit
---

あなたは <PROJECT> の**実装担当**です。設計書と Issue のとおりに作る。**設計判断はしない**（迷いは architect に戻す）。

## やること
1. Issue と設計ファイル、CLAUDE.md を読む。
2. **feature ブランチを切る**。main へ直接コミットしない。
3. 実装する。設計どおりに。
4. **自己検証**: `<検証コマンド>` が PASS すること。UI なら複数幅×ライト/ダーク×各言語で破綻しないか確認する（可能なら Playwright 等で実機確認）。
5. **PR を出す**。本文に「設計ファイルの節・変更点・**検証結果（前後比較の数値を含む）**・触っていない範囲」を書く。

## 禁止（load-bearing）
- **docs/handoff/** を変更しない**（設計正本は architect の領域）。
- 計算仕様は設計書が指示しない限り変えない。
- <プロジェクト固有の不変条件をここに列挙>

## 検証コマンド
`<検証コマンド>`
```

### 2-3. `.claude/agents/reviewer.md`

```markdown
---
name: reviewer
description: <PROJECT> のレビュー＆マージ担当。PR を機械検証＋差分精査し、load-bearing 逸脱がなければ承認コメント→squashマージ→反映確認まで行う。計算に触れる PR は前後比較を必須確認する。
tools: Read, Grep, Glob, Bash, WebFetch
---

あなたは <PROJECT> の**レビュー担当**です。挙動・数値・データを壊す変更を通さないのが仕事。

## 手順
0. **レーン確認**: S レーン（小さな見た目の変更・設計書なし）の PR は軽量レビューでよい。ただし **load-bearing チェックは省略しない**。
1. PR のメタ/本文/差分を把握し、対象ブランチをチェックアウトする。
2. **機械検証**: `<検証コマンド>` を実行し全 PASS を確認。
3. **差分精査**:
   - 「表示のみ」と称する PR が **計算ファイルを触っていないか**
   - ソートやフィルタが**元配列を破壊していないか**（コピー上で操作しているか）
   - **計算 PR** は前後比較の数値が設計書の例と一致するか
   - **リファクタ(挙動不変)** は旧 main と行の多重集合が一致するか（消失0/増加0）
   - load-bearing を侵していないか
4. 問題なければ**承認コメント**（検証結果を要約）→ squash マージ。
5. 反映を確認する。

## 判断基準
検証が1つでも FAIL、または load-bearing 逸脱があればマージしない。
**差分が「表示のみ」の主張と食い違えば実装者に差し戻す。**
```

### 2-4. `.claude/commands/feature.md`

このファイルを置くと `/feature "やりたいこと"` で3人を順に回せます。

```markdown
<PROJECT> の 設計→実装→レビュー パイプラインを次のお題で回す: $ARGUMENTS

手順（各ステップは対応するサブエージェントに委譲する）:
0. **サイズ判定（PM=親が実施）**: お題が **S**（小さな見た目の変更で、計算・データモデル・設定キー・モジュール構成に非接触）なら **architect を省略**し、親が受け入れ条件つきの簡潔な Issue を起票して 2 へ。**迷ったら M/L としてフルで回す。** 関連する小さいお題が複数あれば **1 Issue（箇条書き）＋1PR にまとめてよい**。
1. **architect** サブエージェントで設計する。設計ファイルを新設し、GitHub Issue を起票。Issue番号と設計ファイルのパスを報告させる。仕様に流派/曖昧があり既定で決め切れない場合はここで停止してユーザーに確認する。
1.5 **モック承認（UI テーマのみ）**: 画面構成・レイアウトの再編を含むお題は、実装着手前に PM が**モックを1枚ユーザーへ提示して承認を得る**。文言・余白・色などの S レーンでは不要。
2. **implementer** サブエージェントで、その Issue を feature ブランチで実装する。検証を PASS させ、PR を出す。
3. **reviewer** サブエージェントで PR を検証する。全 PASS かつ load-bearing 逸脱なしなら承認コメント→ squash マージ→ 反映確認。FAIL や逸脱があれば implementer に差し戻す。

並列運用（PM の裁量）:
- 互いに独立なお題（触るファイル群が重ならない）は**別ブランチで並走**してよい。同じファイル群を触るお題は直列。
- お題Nの実装/レビュー中に、お題N+1の **architect を先行起動**してよい。

停止条件: architect が product decision を要する / reviewer が load-bearing 違反を検出 / 検証が FAIL。いずれもユーザーに要点を報告して指示を仰ぐ。
```

## 3. CLAUDE.md に書くこと（ここが一番効く）

エージェント定義より **CLAUDE.md のほうが重要**です。3人全員がこれを読むので、ここに書いたルールが全体に効きます。

### 3-1. サイズ判定のレーン分け

全部をフルパイプラインで回すと、文言修正1つに Issue と設計書ができて割に合いません。

```markdown
## 開発フロー（設計と実装を分ける・一方通行）
着手前に PM がサイズ判定する:
- **S（見た目のみの小変更）**: 文言・余白・要素の削除/移動など、計算・データモデル・
  設定キー・モジュール構成に**非接触**のもの。**architect を省略**し、PM が受け入れ条件つきの
  簡潔な Issue を起票 → implementer が直接実装 → reviewer は軽量レビューのみ。設計書追記なし。
- **M/L（それ以外すべて）**: フルパイプライン。計算・データに触れるものは必ずこちら。
  **判定に迷ったら M/L**。
```

### 3-2. load-bearing（勝手に変えない）リスト

**これが本体です。** 「触ると壊れるもの」を明示的に列挙します。

```markdown
## ★load-bearing（勝手に変えない）
- **<計算式・アルゴリズム>**: 変更は設計書を先に更新してから。
- **<永続化キー>**: データと表示状態は分離する。
- **<i18n のキー集合>**: 全言語で完全一致であること。追加時は全言語同時。
- **<アーキテクチャ上の制約>**: 例「inline onclick がグローバル関数に依存 → ESM 化しない」
- **<デザイン上の意味>**: 例「勝ち=緑/引分=橙/危険=赤 の意味は保持」
```

76-Club の実例（そのまま参考に）:

```markdown
- **§3 の計算式**（ダブルペリア／エブリ／ステーブル／…）。変更は設計書を先に更新してから。
- **localStorage キー**: データ=`golfCompe_v1`／表示状態=`golfCompe_lang`・`_theme`・`_channel`。
  **データと表示状態は分離**（表示状態をデータキーに入れない）。
- **i18n 辞書**は **ja/zh/en のキー集合が完全一致**であること。追加時は3言語同時。
- **inline onclick/onchange はグローバル関数依存** → **ESM 化しない**。読込順は index.html の並び。
- **機能色の"意味"**（勝ち=緑/引分=橙/採用=枠/危険=赤）は保持。
```

### 3-3. 検証コマンドを明記する

```markdown
## 検証（reviewer 必須）
```bash
node tools/verify.mjs    # 構文 / i18n パリティ / 未定義参照 / 未使用キー / 計算回帰
node tools/regress.mjs   # 計算回帰のスナップショット比較
```
```

## 4. 検証の自動化（これが無いと機能しない）

**サブエージェント運用の成否は、ここで決まります。** reviewer が「たぶん大丈夫」としか言えないなら、3人に分けた意味がありません。

### 4-1. 最低限そろえたい2つ

**① 静的検証（verify）** — 壊れていたら即わかるもの

- 構文チェック（`node --check` など）
- 多言語辞書のキー集合が全言語で一致しているか
- コードから参照されているキーが辞書に存在するか（**未定義参照**）
- 辞書にあるがどこからも使われていないキー（**未使用キー**）
- CSS 変数の定義漏れ

**② 回帰テスト（regress）** — 数値が変わったら即わかるもの

固定の入力データに対する計算結果を JSON に保存しておき、毎回比較します。

```
node tools/regress.mjs            # 期待値と比較（差分があれば FAIL）
node tools/regress.mjs --update   # 仕様変更時のみ期待値を更新 → 差分をレビュー
```

### 4-2. これがあると何ができるか

**「既定 OFF の新機能を足しました」を機械的に証明できます。**

```
① 計算ファイルを変更する
② テストケースを足す前に regress を実行 → 差分ゼロ    ← これが証拠
③ そのあと新機能のテストケースを追加して --update
④ 差分が「新ケースの追加だけ」であることを PR で示す
```

この順序を守らせるのが肝です。②を飛ばして③をやると「既存が壊れていないこと」を証明できません。

### 4-3. 「未使用キー検出」の副作用に注意

未使用キー検出を入れると、動的にキーを組み立てるコードが引っかかります。回避策は**キーを文字列リテラルで持つ**ことです。

```js
// ✗ 検出できない
const msg = t('error.' + kind);

// ○ リテラルで持てば検出器が見つけられる
const ERR = { count:'error.count', range:'error.range' };
const msg = t(ERR[kind]);
```

## 5. 実際に効いた運用ルール

76-Club で試行錯誤して定着したものです。**どれも失敗から生まれています。**

### 5-1. まとめ出し（バッチ）

**失敗**: 思いついた順に1つずつ投げたら、Issue/PR/デプロイ確認の固定費ばかりかかった。

**ルール**: 関連する小さい変更が複数あるときは **1 Issue（箇条書き）＋1PR にまとめる**。大きな構造変更は**テーマ単位で要件をまとめて**受け、設計の冒頭で不明点を一括質問する。

### 5-2. モック承認（UI のみ）

**失敗**: 実装してから「思ってたのと違う」で1周やり直し。

**ルール**: 画面構成・レイアウトの再編は、**実装着手前にモック（スクリーンショット1枚）を提示して承認を得る**。モック1枚（約10分）で、実装1周（約30分）の手戻りを防げます。文言・余白・色は不要。

### 5-3. 並列化

- 互いに独立なお題（**触るファイル群が重ならない**）は別ブランチで並走してよい
- 同じファイルを触るお題は**直列**（コンフリクトの解決コストが並列の利得を上回る）
- **お題Nの実装中にお題N+1の設計を先行**させると詰まりにくい（設計ファイルは機能別なので衝突しない）

### 5-4. 設計書は機能別に分ける

1つの巨大な設計書に追記し続けると、複数の architect を並走させたときに必ず衝突します。

```
docs/handoff/
├── 2026-07-12-<プロジェクト正本>.md   ← 計算仕様・データモデルだけ
├── 2026-08-30-univ-match.md           ← 機能ごとに1ファイル
├── 2026-08-31-custom-match.md
└── 2026-09-06-course-master.md
```

**正本への追記は、計算仕様・データモデルに触れる場合だけ**にします。

### 5-5. 数値は必ず実際に計算させる

設計書に「HDCP は 15.6 になる」と書くとき、**推測で書かせない**。node で実際に計算させて、その出力を貼らせます。

実際、設計書の本文と表が矛盾していたケースが 76-Club で1件ありました（実装者が実コードから正しい方を判定し、設計書側を訂正）。

### 5-6. 「できない」と言わせる

外部 API 連携や OCR のような話は、**実現性を正直に評価させて「不採用」も選ばせる**のが大事です。

76-Club では2件とも不採用になりました。

- **スコアカードの写真OCR**: 静的サイトでは外部APIのキーを隠せない／Tesseract は手書きを対象外／`TextDetector` は文字列を返さない → **サーバ側AIを使う市販アプリですら「全ホール手で直した」レビューがある**ことを根拠に不採用
- **コースデータの外部API**: 同じくキーの置き場所がない／CORS の保証がない／日本のデータを返す公開APIが見つからない → 不採用

「調べたが確認できなかった」ことは**「未確認」と明記**させます。推測で埋めさせないためです。

## 6. PM（あなた）の仕事

サブエージェントに任せられないもの、任せてはいけないものです。

| やること | 理由 |
|---|---|
| **サイズ判定（S / M/L）** | 全体の効率を決める。迷ったら M/L |
| **仕様の意思決定** | architect が「未決事項」に上げてきたものを決める |
| **モックの承認取り** | ユーザーとの合意形成 |
| **並列/直列の判断** | 触るファイルが重なるかを見る |
| **エージェント間の情報の受け渡し** | 前の設計の結論を次のプロンプトに書く |
| **Issue/PR/マージ**（環境による） | gh CLI が無い環境では PM が代行 |

### プロンプトの書き方（重要）

サブエージェントは**あなたの会話履歴を見ていません**。毎回、必要な文脈を全部渡します。

```markdown
## 前提（PM が調査済み・これを出発点にしてよい）
<すでに分かっていることを書く。再調査させない>

## ユーザー確定事項
<ユーザーに確認済みの回答を書く。「たぶん〜だろう」で進ませない>

## このPRの範囲（厳守）
触ってよいファイル: A / B / C
触らないファイル: D / E（← 理由も書く）

## 検証（PR本文に貼れる形で実出力を残すこと）
1. <順序が重要な検証はその順序を明示する>
2. ...

## 成果物
1. 実装＋コミット
2. PR 本文のドラフトを <パス> に書き出す
3. 最終報告に「<確認したい具体的な事実>」を明記
```

**「触らないファイル」を明示する**のが特に効きます。これが無いと、良かれと思って関係ないファイルを整形して差分が膨らみます。

## 7. つまずきポイント

### 7-1. サブエージェントは会話を見ていない

同じことを何度も説明する羽目になりますが、**それが正しい**です。文脈を渡し忘れると推測で埋められます。

### 7-2. 「実装済みのはず」を信じない

エージェントの報告は**実出力を貼らせて確認**します。「テストは通りました」ではなく、テストの出力そのものを貼らせます。PM 側でも `verify` を再実行します。

### 7-3. 設計書とコードがズレる

実装中に設計と違う判断が必要になったら、**実装を通してから設計書を直す**（別コミット）。設計書を implementer に直させると、次に読む人が「どちらが正か」わからなくなります。

### 7-4. Issue の記述が古くなる

長く続けると「実装済みだが Issue の記述が当時のまま」になります。クローズするときに**現在の姿との対応表**をコメントで残すと、後から辿れます。

### 7-5. gh CLI が無い環境

クラウドセッションなどで `gh` が使えない場合:

- サブエージェントは **Issue/PR 本文をファイルに書き出す**
- **git は commit まで**（push は PM）
- Issue 起票・PR 作成・マージは PM が GitHub MCP で代行
- 公開確認は直接アクセスできなければ **GitHub Actions の success で代替**

## 8. 30分ではじめる手順

1. **CLAUDE.md に load-bearing リストを書く**（15分）
   「触ると壊れるもの」を5個以上。ここが一番大事で、一番手を抜きやすい。
2. **検証コマンドを1つ作る**（10分）
   最初は構文チェックだけでもいい。`node --check` でも十分。あとから足す。
3. **エージェント3人を置く**（5分）
   §2 のテンプレートをコピーして `<PROJECT>` を置換。
4. **小さいお題で1周回す**
   いきなり大きなことをやらせない。文言修正1つを S レーンで通してみる。
5. **失敗するたびに CLAUDE.md に1行足す**
   これが一番効きます。「またやった」と思ったら、それはルール化のサインです。

## 9. チートシート

```bash
# パイプラインを回す
/feature "やりたいこと"

# 個別に呼ぶ
「architect で <お題> の設計をして」
「implementer で Issue #123 を実装して」
「reviewer で PR #124 を検証して」

# 並列（触るファイルが重ならないとき）
「architect で A の設計、同時に implementer で B の実装を進めて」
```

**判断に迷ったときの原則**

- サイズ判定に迷ったら → **M/L**（フルで回す）
- 設計に迷ったら → **ユーザーに聞く**（既定案を添えて）
- 数値に迷ったら → **実際に計算する**
- 「たぶん大丈夫」と思ったら → **検証を書く**
